# 1.2 Architectural Patterns

This note covers high-level architectural patterns used to organize entire applications or systems of applications.

## Monorepo
A single repository containing multiple distinct projects or packages.
- **Tools:** Lerna, Nx, Turborepo, Yarn/NPM/PNPM Workspaces.
- **Pros:**
    - Simplified dependency management (one `node_modules` at the root).
    - Atomic commits across multiple packages.
    - Easy to share code and enforce standards.
- **Cons:**
    - Tooling can be complex.
    - Can lead to a tightly coupled system if not managed well.
    - CI/CD pipelines need to be configured to only build/test affected packages.

## Polyrepo
The traditional approach where each project or microservice lives in its own repository.
- **Pros:**
    - Clear ownership and separation of concerns.
    - Independent build/deploy pipelines.
- **Cons:**
    - Difficult to share code and manage dependencies across repos (requires a private NPM registry or similar).
    - Cross-repo changes can be complex to coordinate.

## Domain-Driven Design (DDD)
An approach to software development that emphasizes modeling the software to match the real-world domain it represents.
- **Key Concepts:** Bounded Context, Ubiquitous Language, Aggregate, Entity, Value Object.
- **In JS:** Often translates to feature-based folder structures where each "feature" is a "bounded context."

## Clean Architecture
A software design philosophy that separates the elements of a design into ring-like levels. The main rule is that code dependencies can only move from the outer levels inward.
- **Layers:**
    - **Entities:** Application-independent business rules.
    - **Use Cases:** Application-specific business rules.
    - **Interface Adapters:** Gateways, Presenters. Convert data for use cases and UI.
    - **Frameworks & Drivers:** The outermost layer (UI, DB, Web Frameworks).
- **Goal:** To create a system that is independent of frameworks, UI, and database, making it highly testable and maintainable.
