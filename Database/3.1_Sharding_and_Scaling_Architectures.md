# Sharding and Scaling Architectures

When a single database server can no longer handle the load (CPU, Memory, or Disk I/O), you must scale.

## 1. Vertical vs. Horizontal Scaling

### 1.1 Vertical Scaling (Scaling Up)
Adding more RAM/CPU to the same machine.
- **Pros:** Zero code changes.
- **Cons:** Hard hardware limit and exponentially increasing costs.

### 1.2 Horizontal Scaling (Scaling Out)
Adding more machines to the cluster. This is where **Sharding** comes in.

## 2. Table Partitioning (PostgreSQL)
Before sharding, use partitioning. It splits a table into smaller physical pieces within the *same* database.
- **Range Partitioning:** By date (e.g., `orders_2023`, `orders_2024`).
- **List Partitioning:** By region (e.g., `users_us`, `users_eu`).
- **Hash Partitioning:** Distributing rows evenly using a hash of a key.

## 3. Sharding (Multi-Node Scaling)
Sharding is the process of breaking a single database into several smaller ones across different servers.

### 3.1 Choosing a Shard Key
The most critical decision. A bad shard key leads to "Hotspots".
- **Good Shard Key:** High cardinality, even distribution (e.g., `user_id` for a social app).
- **Bad Shard Key:** Low cardinality (e.g., `gender`) or monotonically increasing values (e.g., `created_at` can create hotspots on the latest shard).

### 3.2 Sharding Logic Location
1.  **Application Level:** The app code decides which shard to query. (Hard to maintain).
2.  **Proxy Level:** A middle-ware (like **Vitess** for MySQL or **Citus** for Postgres) routes queries automatically.
3.  **Database Level:** Native sharding (e.g., MongoDB, CockroachDB).

## 4. Challenges of Sharding
- **No Global Joins:** Joining tables across shards is nearly impossible or extremely slow.
- **No Global Transactions:** ACID properties across shards require complex Two-Phase Commits (2PC).
- **Resharding:** Moving data when a shard gets too full is a massive operational headache.
