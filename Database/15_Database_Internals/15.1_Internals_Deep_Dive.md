# Phase 7 & 15: Database Internals & Transactions

This is the senior-level knowledge that separates engineers from coders.

## 1. Transactions & Concurrency (Phase 7)

### 1.1 Locking Models
- **Optimistic Locking:** Assume conflicts are rare. Use a `version` or `updated_at` column. If it changed between read and write, fail the transaction.
- **Pessimistic Locking:** Assume conflicts will happen. Use `SELECT ... FOR UPDATE` to lock the row.

### 1.2 Race Conditions
- **Double Spending Problem:** Two transactions withdrawing $100 from a $150 balance simultaneously.
- **Lost Updates:** Two transactions overwriting each other's changes.

### 1.3 Isolation Levels
1.  **Read Uncommitted:** Dirty reads allowed.
2.  **Read Committed:** Only committed data (Default).
3.  **Repeatable Read:** Data won't change during the transaction (Snapshot).
4.  **Serializable:** Transactions act as if they are strictly sequential.

## 2. Database Internals (Phase 15)

### 2.1 How B-Trees Work
- **Structure:** Root -> Internal Nodes -> Leaf Nodes (Linked).
- **Fan-out:** High fan-out keeps the tree shallow (e.g., 3 levels for 10M rows).

### 2.2 The Write-Ahead Log (WAL)
- Every change is written to the WAL *sequentially* before being applied to the data files. This ensures Durability with high performance.

### 2.3 MVCC (Multi-Version Concurrency Control)
- Postgres creates a new version of a row on every `UPDATE`.
- **xmin / xmax:** Hidden columns that track which transaction created and deleted a row.
- **Vacuuming:** The background process that cleans up these "dead tuples" to prevent table bloat.

### 2.4 Storage Engines: LSM Trees vs B-Trees
- **B-Trees:** Best for Read-heavy workloads (Postgres).
- **LSM Trees (Log-Structured Merge-Tree):** Best for Write-heavy workloads (Cassandra/ScyllaDB). Uses **SSTables** (Sorted String Tables).
- **Buffer Pool:** A region of RAM where the DB caches pages from disk.
