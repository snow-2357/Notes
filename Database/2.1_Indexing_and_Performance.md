# Deep Dive: Indexing Strategies

Indexes are the single most important tool for database performance. Understanding how they work internally is key to designing high-performance schemas.

## 1. B-Tree Indexes (The Default)
A B-Tree (Balanced Tree) keeps data sorted and allows for binary-search-like lookups.
- **Complexity:** `O(log N)`.
- **Best for:** Equality (`=`), Range (`>`, `<`), and Prefix sorting.
- **Internal Structure:** Root node -> Branch nodes -> Leaf nodes (pointing to actual data).

## 2. Specialized Postgres Index Types

### 2.1 GIN (Generalized Inverted Index)
Ideal when one column value contains multiple "keys".
- **Use Case:** JSONB columns, Full-Text Search, Arrays.
- **Example:** `CREATE INDEX idx_tags ON products USING GIN (tags);`

### 2.2 BRIN (Block Range Index)
Extremely small indexes for massive tables where data is naturally sorted.
- **How it works:** Instead of indexing every row, it stores the Min/Max value for a range of blocks (e.g., 1MB chunks).
- **Use Case:** Time-series data (Log tables).

### 2.3 Partial Indexes
Index only a subset of the table.
- **Benefit:** Reduces index size and maintenance cost.
- **Example:** `CREATE INDEX idx_active_users ON users (id) WHERE status = 'active';`

### 2.4 Covering Indexes (Index-Only Scans)
An index that includes all the columns requested in the `SELECT` statement.
- **Benefit:** The database doesn't have to "heap fetch" (go to the table file) at all.
- **Example:** `CREATE INDEX idx_user_email_name ON users (email) INCLUDE (name);`

## 3. When to Avoid Indexes
1.  **Low Cardinality:** Columns with very few unique values (e.g., `is_deleted` or `gender`). The DB engine will likely prefer a full table scan.
2.  **Frequent Writes:** Every index adds overhead to `INSERT`, `UPDATE`, and `DELETE` operations.
3.  **Small Tables:** If the entire table fits in a few memory pages, indexing is overkill.
