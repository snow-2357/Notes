# Phase 7: Transactions & Concurrency

How databases maintain data integrity in a multi-user environment.

## 1. Transaction Life Cycle
- **BEGIN / START TRANSACTION:** Mark the start of a logical unit of work.
- **COMMIT:** Persist all changes to disk permanently.
- **ROLLBACK:** Revert all changes if an error occurs.
- **Savepoints:** Create markers within a transaction to rollback partially.

## 2. Concurrency Issues (The "Big Three")
- **Dirty Reads:** Transaction A reads data modified by B but not yet committed.
- **Non-Repeatable Reads:** Transaction A reads a row, B updates/commits it, A reads again and sees different data.
- **Phantom Reads:** Transaction A reads a set of rows, B inserts/commits a new row that matches A's filter, A reads again and sees a "phantom" row.

## 3. Locking Strategies
- **Row-Level Locks:** Locks specific rows (Postgres default). High concurrency.
- **Table-Level Locks:** Locks the whole table. Zero concurrency (Used for schema changes).
- **Pessimistic Locking:** `SELECT ... FOR UPDATE`. "I'm definitely changing this, don't let anyone else touch it."
- **Optimistic Locking:** Using a `version` column. "I hope nobody changed this while I was working; if they did, fail my update."

## 4. MVCC (Multi-Version Concurrency Control)
Postgres's implementation of concurrency.
- Instead of locking, it keeps multiple versions of a row.
- **Snapshots:** Each transaction sees a consistent snapshot of the data at a specific point in time.
- **xmin / xmax:** Hidden columns identifying the creating and deleting transactions.

## 5. Real-World Problem: The Double Spending Problem
1.  User A has $100.
2.  Transaction 1 (Withdraw $80) and Transaction 2 (Withdraw $80) start at the same time.
3.  Both read balance as $100.
4.  Both update balance to $20.
- **Solution:** Use **Serializable Isolation** or **Pessimistic Locking** (`SELECT FOR UPDATE`) on the balance row to ensure T2 waits for T1 to finish.
