# Phase 8 & 9: Scaling, Partitioning & Sharding

How to handle millions of users and terabytes of data.

## 1. Scaling Strategies (Phase 8)
- **Vertical Scaling:** Bigger machine (RAM/CPU). Limited by physics.
- **Horizontal Scaling:** More machines. Requires a distributed architecture.
- **Replication:**
    - **Leader-Follower:** Writes go to Leader, Reads go to Replicas.
    - **Read Replicas:** Scales Read traffic.
    - **Failover:** Promoting a replica to Leader if the main node dies.

## 2. Connection Management
- **Connection Pooling:** DB connections are expensive. Use tools like **PgBouncer** to reuse them.
- **Caching:** Use **Redis** to store frequent query results and reduce DB load.

## 3. Partitioning & Sharding (Phase 9)

### 3.1 Partitioning (Logical)
Splitting a table into smaller physical pieces on the **same** server.
- **Range:** `orders_2023`, `orders_2024`.
- **List:** `users_us`, `users_eu`.
- **Hash:** `hash(id) % 4`.

### 3.2 Sharding (Physical)
Splitting data across **different** servers.
- **Shard Key:** The column used to decide where data goes. Must be evenly distributed.
- **Consistent Hashing:** Minimizes data movement when adding shards.
- **Hot Partitions:** When one shard gets too much traffic (e.g., a "Celebrity" user in a social app).

### 3.3 The Challenges
- **Distributed Transactions:** Very slow.
- **Replication Lag:** When a Read Replica is slightly behind the Leader.
- **Cross-shard Joins:** Almost impossible; requires denormalization.
