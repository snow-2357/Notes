# Phase 9: Partitioning & Sharding

Advanced strategies for handling massive datasets.

## 1. Table Partitioning (Logical Separation)
Splitting a large table into smaller physical pieces (partitions) within a single database server.

- **Range Partitioning:** By a range of values (e.g., `created_at` date ranges).
- **List Partitioning:** By a set of values (e.g., `country_code`).
- **Hash Partitioning:** Distributing rows using a hash function (e.g., `user_id % 4`).

### 1.1 Benefits
- **Partition Pruning:** The query planner skips partitions that cannot possibly contain the requested data.
- **Improved Maintenance:** Faster VACUUMing and the ability to drop old data by simply dropping a partition.

## 2. Database Sharding (Physical Separation)
Distributing data across multiple independent database servers (shards).

- **The Shard Key:** The column used to determine which shard a row belongs to.
- **Shard Mapping:**
    - **Algorithmic (Hash-based):** `shard_id = hash(user_id) % num_shards`.
    - **Directory-based:** A lookup table maps keys to shard IDs.

## 3. Critical Sharding Challenges
- **Consistent Hashing:** A method to add/remove shards without re-sharding all existing data.
- **Hot Partitions:** When one shard receives significantly more traffic (e.g., a high-profile user on a social network).
- **Cross-Shard Joins:** Extremely slow and complex. Usually avoided by denormalizing data or performing joins in the application layer.
- **Distributed Transactions:** Ensuring ACID across shards. Usually requires Two-Phase Commit (2PC) or Sagas.

## 4. Operational Headaches
- **Rebalancing:** Moving data between shards as the cluster grows.
- **Global IDs:** You cannot use `SERIAL` or `AUTO_INCREMENT` because IDs will collide across shards.
    - *Solutions:* UUIDs, Snowflake IDs, or a centralized ID generator.
- **Replication Lag:** The time it takes for a write on the leader to reach the read replicas.
