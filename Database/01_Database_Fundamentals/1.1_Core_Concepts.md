# Phase 1: Database Fundamentals

The foundation of database engineering starts here.

## 1. What is a DBMS?
A **Database Management System (DBMS)** is software that interacts with end-users, applications, and the database itself to capture and analyze data.
- **RDBMS (Relational):** Data is organized into tables with predefined schemas. (Postgres, MySQL).
- **NoSQL (Non-Relational):** Data is document-based, key-value, or graph-based. (MongoDB, Redis).

## 2. The Relational Model
- **Table:** A collection of related data entries.
- **Row (Tuple):** A single record in a table.
- **Column (Attribute):** A field in a table.

### 2.1 Keys & Constraints
- **Primary Key (PK):** A unique identifier for every row. Cannot be NULL.
- **Foreign Key (FK):** A field that links one table to the PK of another table.
- **Constraints:**
    - `NOT NULL`: Column cannot have a NULL value.
    - `UNIQUE`: All values in a column must be different.
    - `CHECK`: Ensures all values in a column satisfy a specific condition.

## 3. Normalization (Data Integrity)
Normalization is the process of structuring a database to reduce redundancy and prevent **Data Anomalies** (errors that happen when you update, delete, or insert data).

### 3.1 1NF (First Normal Form): Atomic Values
**The Rule:** A table is in 1NF if every cell contains only one single (atomic) value, and there are no repeating groups/arrays.

*   **What it means:** You can't put a list of things (like "Apples, Oranges") in a single box.
*   **The "Bad" Way:**
    | UserID | Name | Phones |
    | :--- | :--- | :--- |
    | 1 | Alice | 555-0101, 555-0102 |
*   **The "Good" Way (1NF):**
    | UserID | Name | Phone |
    | :--- | :--- | :--- |
    | 1 | Alice | 555-0101 |
    | 1 | Alice | 555-0102 |

### 3.2 2NF (Second Normal Form): No Partial Dependencies
**The Rule:** The table must be in 1NF **AND** every non-key column must depend on the **whole** primary key.

*   **What it means:** This only matters when you have a **Composite Key** (a primary key made of two or more columns). If a column only cares about *part* of that key, it doesn't belong there.
*   **The "Bad" Way:** (Key is `ProjectID + EmployeeID`)
    | ProjectID | EmployeeID | Hours_Worked | Employee_Name |
    | :--- | :--- | :--- | :--- |
    | P1 | E10 | 40 | Alice |
    *Problem:* `Employee_Name` only depends on `EmployeeID`. It doesn't care about the `ProjectID`. This is a "Partial Dependency."
*   **The "Good" Way (2NF):** Split it into two tables.
    1.  **Projects_Employees:** `ProjectID`, `EmployeeID`, `Hours_Worked`
    2.  **Employees:** `EmployeeID`, `Employee_Name`

### 3.3 3NF (Third Normal Form): No Transitive Dependencies
**The Rule:** The table must be in 2NF **AND** no non-key column should depend on another non-key column.

*   **What it means:** A -> B -> C. If A is the PK, and C depends on B, then C has a "transitive dependency" on A. C should be in its own table with B.
*   **The "Bad" Way:** (Key is `OrderID`)
    | OrderID | CustomerID | Customer_City |
    | :--- | :--- | :--- |
    | 501 | C99 | New York |
    *Problem:* `Customer_City` depends on `CustomerID`, which is not the primary key. If you change a customer's city, you'd have to update every single order they ever made.
*   **The "Good" Way (3NF):**
    1.  **Orders:** `OrderID`, `CustomerID`
    2.  **Customers:** `CustomerID`, `Customer_City`

### 3.4 Why do we do this? (Anomalies)
1.  **Update Anomaly:** If Alice changes her name, you shouldn't have to update 50 rows in the "Projects" table.
2.  **Insert Anomaly:** You can't record a new employee's name unless they are assigned to a project (if the key is `ProjectID + EmployeeID`).
3.  **Delete Anomaly:** If you delete the last project for a department, you accidentally delete the department's name from your system.

### 3.1 Denormalization
The process of adding redundant data to speed up complex queries. Often used in Read-heavy systems or Analytics.

## 4. ACID Properties (The Transactional Gold Standard)
1.  **Atomicity:** All-or-nothing. If one part fails, the whole transaction fails.
2.  **Consistency:** The DB moves from one valid state to another.
3.  **Isolation:** Transactions occur independently of each other.
4.  **Durability:** Once committed, data remains even in a system failure.

## 5. CAP Theorem (The Distributed Trade-off)
In a distributed system, you can only pick **two**:
- **Consistency:** Every read receives the most recent write.
- **Availability:** Every request receives a response (not guaranteed to be the latest).
- **Partition Tolerance:** The system continues to work despite network failures.
