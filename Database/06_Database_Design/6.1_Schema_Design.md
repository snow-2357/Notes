# Phase 6: Database Design & Schema Architecture

Design is about knowing when to normalize for consistency and when to denormalize for performance.

## 1. Entity Relationships
- **One-to-One (1:1):** User -> Profile.
- **One-to-Many (1:M):** User -> Posts.
- **Many-to-Many (M:M):** Students -> Courses (Requires a **Junction Table**).

## 2. Design Patterns for Modern Apps

### 2.1 Ecommerce Schema
- **Tables:** Users, Products, Categories, Orders, Order_Items, Cart.
- **Junction:** `Order_Items` links `Orders` to `Products`.
- **Constraint:** Use `DECIMAL` for prices, never `FLOAT`.

### 2.2 Social Media / Chat
- **Self-Referential:** `Followers` (user_id -> user_id).
- **Audit Tables:** Recording every change to a record for compliance.
- **Soft Delete:** Using a `deleted_at` timestamp instead of deleting rows.
- **Versioning:** Storing previous versions of a row (e.g., `product_history`).

## 3. When to Normalize vs Denormalize
- **Normalize (3NF/BCNF):** For Write-heavy, transactional systems like **Banking**. Data integrity is paramount.
- **Denormalize:** For Read-heavy, analytical systems like a **Social Feed**. Speed is more important than avoiding redundancy.

## 4. Specific Design Exercises
- **Chat App:** Designing for high-concurrency message storage.
- **Ride Booking:** Handling real-time location and trip state.
- **Expense Tracker:** Categories, Recurring transactions, and Multi-currency support.
