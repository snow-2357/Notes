# Phase 13: Real World Data Patterns

How architectural patterns dictate how data flows through a backend system.

## 1. Event Sourcing
Instead of storing the current state of an object, store the sequence of state-changing events.
- **Why?** Perfect audit log, ability to "time travel" to any previous state, and easy debugging.
- **Challenge:** Replaying 1 million events to get the current state is slow. Use **Snapshots** to cache the state at specific intervals.

## 2. CQRS (Command Query Responsibility Segregation)
Separating the logic for updating data (Commands) from the logic for reading data (Queries).
- **Writes:** Optimized for consistency and business logic (Normalized DB).
- **Reads:** Optimized for the UI (Denormalized, potentially in a different DB like Elasticsearch or Redis).

## 3. The Outbox Pattern
Ensuring atomicity between a database update and publishing an event to a message broker (like Kafka/RabbitMQ).
1.  Transaction starts.
2.  Update the business table.
3.  Insert the message into an `outbox` table in the **same** database.
4.  Commit transaction.
5.  A separate "Relay" service polls the `outbox` table and publishes the message.

## 4. Idempotency
Ensuring that the same request sent multiple times results in the same outcome.
- **Pattern:** The client sends an `idempotency-key` (UUID). The server checks if it has already processed this key before doing any work.

## 5. Soft Delete
Using a flag (e.g., `is_deleted = true`) or a timestamp (`deleted_at`) instead of physically removing rows.
- **Why?** Accident recovery, audit trails, and maintaining referential integrity.
- **Optimization:** Use a **Partial Index** (`WHERE deleted_at IS NULL`) to keep queries fast.

## 6. Time-Series Data
Optimizing for data where time is the primary axis (logs, metrics, stock prices).
- **Pattern:** Group data into "Buckets" or "Chunks" by time to allow for massive throughput and efficient range scans.
- **Retention Policies:** Automatically moving old data to cheaper storage or deleting it.

## 7. Append-Only Logs
Data is only ever added to the end.
- **Why?** Extremely fast writes (no random I/O). Used internally by WAL and externally by high-throughput systems like Kafka.
