# SQL and PostgreSQL Deep Dive

This note covers the internals of how relational databases work, focusing on PostgreSQL, indexing strategies, sharding, and advanced SQL querying.

## 1. How Databases Work (Internals)

### 1.1 The Storage Engine
At its core, a database is a file system optimized for retrieval.
- **Pages/Blocks:** Data is stored in fixed-size chunks (usually 8KB in Postgres).
- **Buffer Pool:** A region of memory where the DB caches pages to avoid disk I/O.
- **WAL (Write-Ahead Logging):** Every change is first written to a log (WAL) before being applied to the data files. This ensures durability (the 'D' in ACID).

### 1.2 Data Structures: B-Trees
Most relational databases use **B-Trees** (or B+Trees) for indexing.
- **Logarithmic Search:** `O(log n)` lookup time.
- **Balance:** The tree stays balanced regardless of insertions/deletions.
- **Range Queries:** B+Trees are excellent for range queries because the leaf nodes are linked.

## 2. Indexing Strategies

### 2.1 Clustered vs. Non-Clustered Indexes
- **Clustered Index:** Defines the physical order of data in the table. A table can only have one (usually the Primary Key).
- **Non-Clustered Index:** A separate structure that contains the indexed columns and a pointer (CTID in Postgres) to the actual row.

### 2.2 PostgreSQL Index Types
- **B-Tree:** Default, best for equality and range queries.
- **GIN (Generalized Inverted Index):** Best for JSONB, arrays, and full-text search.
- **GiST:** Useful for geometric data and custom data types.
- **BRIN (Block Range Index):** For very large tables where data is naturally sorted (e.g., timestamps).

## 3. Sharding and Partitioning

### 3.1 Table Partitioning (Horizontal)
Splitting one large table into smaller physical pieces (partitions) based on a key (e.g., `created_at`).
- **Benefits:** Faster vacuuming, better query performance via **Partition Pruning**.

### 3.2 Sharding (Database Splitting)
Distributing data across multiple independent database instances.
- **Vertical Sharding:** Splitting by columns (rare for scaling).
- **Horizontal Sharding:** Splitting by rows. A "Sharding Key" determines which shard holds which row.
- **Challenge:** Joins across shards are extremely difficult and slow.

---

## 4. PostgreSQL Specifics: MVCC
PostgreSQL uses **Multi-Version Concurrency Control**.
- Instead of locking rows for every read/write, Postgres keeps multiple versions of a row.
- **VACUUM:** The process of cleaning up "dead tuples" (old versions of rows) that are no longer needed.

## 5. Advanced SQL Queries

### 5.1 Common Table Expressions (CTEs)
Useful for breaking down complex queries.
```sql
WITH regional_sales AS (
    SELECT region, SUM(amount) AS total_sales
    FROM orders
    GROUP BY region
)
SELECT region
FROM regional_sales
WHERE total_sales > (SELECT SUM(total_sales)/10 FROM regional_sales);
```

### 5.2 Window Functions
Perform calculations across a set of table rows that are related to the current row.
```sql
SELECT 
    name, 
    department, 
    salary,
    RANK() OVER (PARTITION BY department ORDER BY salary DESC) as salary_rank
FROM employees;
```

### 5.3 Complex Joins
- **LATERAL JOIN:** Allows a subquery in the FROM clause to refer to columns of preceding items in the FROM list (like a for-each loop in SQL).
```sql
SELECT authors.name, recent_books.title
FROM authors
LEFT JOIN LATERAL (
    SELECT title 
    FROM books 
    WHERE books.author_id = authors.id 
    ORDER BY published_date DESC 
    LIMIT 2
) AS recent_books ON true;
```
