# 5.2 Development Ecosystem & Tooling

Writing code is only one part of modern development. A rich ecosystem of tools exists to help you manage dependencies, ensure code quality, and bundle your code for production.

## Package Managers (npm & yarn)

A package manager automates the process of installing, updating, and managing third-party libraries (or "packages") that your project depends on.

-   **`npm`** (Node Package Manager): The default package manager that comes with Node.js.
-   **`yarn`**: A popular alternative to npm, developed by Facebook. It was created to be faster and more reliable than older versions of npm. Modern npm has caught up, but yarn is still widely used.

**Key Files:**
-   **`package.json`**: This file is the manifest of your project. It contains metadata like the project's name and version, and lists all its dependencies.
-   **`node_modules/`**: The folder where all the actual code for your project's dependencies is downloaded and stored. You should **never** commit this folder to version control (add it to your `.gitignore` file).
-   **`package-lock.json`** (npm) or **`yarn.lock`** (yarn): These are lock files. They record the exact version of every dependency that was installed. This ensures that every developer on the team, and your deployment server, gets the exact same set of dependencies, preventing "it works on my machine" bugs.

**Common Commands:**
| Action                     | npm                             | yarn                    |
| -------------------------- | ------------------------------- | ----------------------- |
| **Initialize Project**     | `npm init`                      | `yarn init`             |
| **Install from lock file** | `npm install` (or `npm i`)      | `yarn install` (or just `yarn`) |
| **Add a dependency**       | `npm install <package-name>`    | `yarn add <package-name>` |
| **Add a dev dependency**   | `npm install --save-dev <pkg>`  | `yarn add --dev <pkg>`  |
| **Remove a dependency**    | `npm uninstall <package-name>`  | `yarn remove <package-name>`|
| **Run a script**           | `npm run <script-name>`         | `yarn <script-name>`    |


## Code Quality: Linters & Formatters

These tools help keep your code consistent, readable, and free of common errors.

### Linters (e.g., ESLint)
A linter analyzes your code for programmatic and stylistic errors based on a set of configurable rules. It can catch potential bugs, enforce best practices, and identify "code smells."

-   **ESLint** is the standard linter for the JavaScript/TypeScript ecosystem.
-   It is highly configurable via an `.eslintrc.js` file.
-   It can be integrated directly into your code editor to provide real-time feedback.

**Example Rules:**
-   `no-unused-vars`: Warns if a variable is declared but never used.
-   `eqeqeq`: Enforces the use of `===` instead of `==`.
-   `no-console`: Disallows the use of `console.log` in production code.

### Formatters (e.g., Prettier)
A code formatter automatically reformats your code to conform to a specific style guide. It doesn't check for correctness, only for style (indentation, spacing, line breaks, etc.).

-   **Prettier** is an "opinionated" code formatter. It has very few options to configure.
-   The goal of Prettier is to end all debates about code style. The team agrees on a style, configures Prettier, and it's applied automatically.
-   It's often run automatically when you save a file or before you commit code.

**Linter vs. Formatter:**
-   A **Linter** is about the **correctness** and **quality** of your code.
-   A **Formatter** is about the **style** and **consistency** of your code's appearance.

They work best together. ESLint can identify a bug, and Prettier can fix the formatting. Many starter kits come with both pre-configured to work in harmony.
