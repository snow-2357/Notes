# Contributor's Guide to Turborepo Internals

This document provides a deep dive into the architecture and internal mechanics of Turborepo, aimed at potential contributors and engineers interested in high-performance build systems.

---

## 1. Project Philosophy: The Move to Rust
Turborepo was originally written in Go but underwent a full rewrite to Rust. This transition was driven by several strategic engineering goals:

*   **Shared Infrastructure (The "Turbo Engine"):** Vercel unified the core incremental computation engine used by both **Turborepo** (the task runner) and **Turbopack** (the bundler). Since Turbopack requires deep integration with Rust-based tools like the SWC compiler, Rust became the standard.
*   **Memory Efficiency:** For massive monorepos (500+ packages), managing the Task Graph and file system state in memory without a Garbage Collector (GC) prevents "stop-the-world" pauses and reduces peak memory usage.
*   **Fearless Concurrency:** Utilizing `Rayon` for parallel file hashing and `Tokio` for asynchronous I/O allows Turborepo to saturate CPU cores safely while walking complex dependency graphs.

---

## 2. Repository Structure
As a contributor, the codebase is split between a high-performance Rust core and a TypeScript ecosystem:

*   **`crates/` (The Rust Core):**
    *   `turbo-engine`: The low-level incremental computation framework. It handles memoization and tracks inputs/outputs.
    *   `turbo-repository`: Logic for understanding monorepo structures (workspaces, `package.json` resolution, lockfile parsing).
    *   `turbo-cli`: The entry point that bridges user commands to the engine.
*   **`packages/` (TypeScript Ecosystem):**
    *   Contains helper packages like `eslint-config-turbo`, `create-turbo`, and various internal utilities.

## 3. Core Technical Concepts

### A. The Hashing Engine
The "Cache Hit" logic is powered by a deterministic hashing system. A task's hash (the "Fingerprint") is generated by combining:
1.  **File Inputs:** Hashes of all files matched by the `inputs` glob in `turbo.json`.
2.  **Environment Variables:** Any `$VARS` specified in the task configuration.
3.  **Dependency Graph:** The hashes of all upstream tasks (if `App A` depends on `Lib B`, the hash of `Lib B` is an input for `App A`).
4.  **Task Configuration:** The specific command and arguments being run.

### B. The Task Graph (DAG)
Turborepo converts your `turbo.json` into a **Directed Acyclic Graph (DAG)**. 
*   **Nodes:** Represent individual tasks (e.g., `dashboard#build`).
*   **Edges:** Represent dependencies (e.g., `build` depends on `topo`).
*   **Execution:** The scheduler traverses the DAG. If a node is cached, it replays the artifacts; if not, it executes the task and caches the result for future runs.

### C. The Daemon
To avoid the overhead of re-scanning thousands of files on every execution, Turborepo uses a persistent background **File Daemon**.
*   It maintains an in-memory representation of the file system.
*   It uses native OS events (like `fsevent` or `inotify`) to update the state instantly when files change.

## 4. Contributor Workflow
1.  **Environment:** Requires `rustup` (Rust toolchain) and `pnpm`.
2.  **Build:** Run `cargo build` from the root to compile the Rust binary.
3.  **Testing:** The `turborepo-tests/` directory contains integration tests that run the compiled `turbo` binary against various monorepo templates to ensure no regressions in hashing or caching logic.
