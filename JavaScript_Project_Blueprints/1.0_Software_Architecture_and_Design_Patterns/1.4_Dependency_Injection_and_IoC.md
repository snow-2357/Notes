# 1.4 Dependency Injection and Inversion of Control

## Inversion of Control (IoC)
A principle in software engineering by which control of objects or portions of a program is transferred to a container or framework. It's about "don't call us, we'll call you."

A simple example is a framework's lifecycle methods. You don't call the `render` method in React; the framework does. You just define what it should do.

## Dependency Injection (DI)
A specific pattern for implementing IoC. Instead of a component creating its own dependencies, the dependencies are "injected" from an external source (the "injector").

### Why use DI?
- **Decoupling:** Components are not responsible for creating their dependencies, so they are not tied to specific implementations.
- **Testability:** It's easy to "inject" mock or fake dependencies during testing.
- **Flexibility:** You can change the implementation of a dependency without changing the component that uses it.

### Forms of DI in JavaScript/TypeScript

1.  **Constructor Injection (Most Common):** Dependencies are provided through the class constructor.

    ```typescript
    class UserService {
      constructor(private apiClient: ApiClient) {}

      getUsers() {
        return this.apiClient.get('/users');
      }
    }

    // In the injector/container:
    const apiClient = new ProductionApiClient();
    const userService = new UserService(apiClient);
    ```

2.  **Property Injection:** Dependencies are set through public properties. Less common, can lead to objects being in an invalid state.

3.  **Method Injection:** The dependency is passed directly to the method that needs it. Useful when only one method needs the dependency.

### DI Containers
Libraries that automate the process of creating and injecting dependencies.
- **Examples:** InversifyJS, NestJS (built-in), TypeDI.
- They manage the lifecycle of services (e.g., singleton, transient) and resolve dependency graphs automatically.
