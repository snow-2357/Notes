# 1.4 Rate Limiting Approaches

Rate limiting is a strategy used to control the rate at which an API or service is accessed. It restricts the number of requests a user, IP address, or client can make within a given time window. This is a crucial defense mechanism for backend services, providing several benefits:

## Why Implement Rate Limiting?
*   **Prevent Abuse and Attacks:** Protects against various malicious activities like brute-force attacks, Denial of Service (DoS) attacks, web scraping, and spamming.
*   **Resource Management:** Prevents a single client from monopolizing server resources, ensuring fair access for all legitimate users.
*   **Cost Control:** For services that incur costs based on usage (e.g., cloud API calls, database queries), rate limiting helps control expenses.
*   **API Stability:** Maintains service stability and availability under high load or unexpected traffic spikes.
*   **Fair Usage:** Ensures that the service remains responsive for everyone.

## Common Rate Limiting Algorithms:

1.  **Fixed Window Counter:**
    *   **How it works:** A counter is maintained for a fixed time window (e.g., 1 minute). Each request increments the counter. If the counter exceeds the limit within the window, subsequent requests are blocked.
    *   **Pros:** Simple to implement.
    *   **Cons:** Can allow a "burst" of requests at the edge of the window. For example, if the limit is 100 requests/minute, a user could make 100 requests in the last second of minute 1 and 100 requests in the first second of minute 2, effectively making 200 requests in 2 seconds.

2.  **Sliding Window Log:**
    *   **How it works:** Instead of a single counter, this method keeps a log of timestamps for each request. When a new request arrives, it removes all timestamps older than the current window and counts the remaining timestamps. If the count exceeds the limit, the request is blocked.
    *   **Pros:** Very accurate, avoids the "burst" problem of fixed window.
    *   **Cons:** More memory-intensive due to storing all timestamps, and CPU-intensive due to the need to iterate over timestamps.

3.  **Sliding Window Counter (Hybrid):**
    *   **How it works:** A more practical approach that combines elements of fixed window and sliding window log. It divides the time into fixed windows but calculates the rate based on a weighted average of the current window's count and the previous window's count.
    *   **Pros:** Good balance of accuracy and efficiency.
    *   **Cons:** More complex than fixed window.

4.  **Token Bucket:**
    *   **How it works:** A "bucket" with a fixed capacity for "tokens" is created. Tokens are added to the bucket at a constant rate. Each request consumes one token. If a request arrives and the bucket is empty, the request is blocked.
    *   **Pros:** Allows for bursts of requests up to the bucket's capacity. Flexible and can handle varying traffic patterns well.
    *   **Cons:** More complex to implement, especially for distributed systems.

5.  **Leaky Bucket:**
    *   **How it works:** Similar to a water bucket with a hole at the bottom. Requests fill the bucket (water), and requests "leak" out at a constant rate (drip). If the bucket overflows (gets too full), new requests are dropped.
    *   **Pros:** Smoothes out bursty traffic, ensuring a steady output rate.
    *   **Cons:** Doesn't handle bursts as well as Token Bucket, can lead to request dropping even if capacity could have handled it.

## Where to Implement Rate Limiting:

*   **API Gateway/Load Balancer:** (e.g., Nginx, AWS API Gateway, Cloudflare) - Ideal for global, infrastructure-level rate limiting before requests even hit your application servers.
*   **Application Middleware:** (e.g., in Node.js with Express) - For fine-grained control based on user IDs, specific API endpoints, or custom business logic.
*   **Service Mesh:** (e.g., Istio) - For microservices architectures.

## Implementation Considerations for Node.js (with Express):

1.  **Storage:** Where will you store the counters/timestamps?
    *   **In-memory:** Simplest for single-instance applications, but state is lost on restart and doesn't scale across multiple instances.
    *   **Redis:** Most common and recommended for distributed Node.js applications. Provides fast, in-memory key-value storage suitable for counters, timestamps, or tokens.
    *   **Database:** Less ideal for high-throughput rate limiting due to latency, but can be used for very low-volume APIs.

2.  **Libraries:** Use battle-tested libraries.
    *   For Express: `express-rate-limit` (often backed by Redis).
    *   For more generic use: `rate-limiter-flexible`.

## Example with `express-rate-limit` (using in-memory store by default):

```javascript
const express = require('express');
const rateLimit = require('express-rate-limit');

const app = express();

// Apply to all requests
const apiLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 100, // Limit each IP to 100 requests per windowMs
  message: 'Too many requests from this IP, please try again after 15 minutes',
  standardHeaders: true, // Return rate limit info in the `RateLimit-*` headers
  legacyHeaders: false, // Disable the `X-RateLimit-*` headers
});

// Apply to a specific route
const loginLimiter = rateLimit({
  windowMs: 60 * 60 * 1000, // 1 hour
  max: 5, // Limit each IP to 5 login requests per hour
  message: 'Too many login attempts from this IP, please try again after an hour',
  standardHeaders: true,
  legacyHeaders: false,
});

// Apply the general API limiter to all requests
app.use(apiLimiter);

// Apply a more restrictive limiter to the login route
app.post('/login', loginLimiter, (req, res) => {
  // Handle login logic
  res.send('Login successful (or attempt failed)');
});

app.get('/api/data', (req, res) => {
  res.send('Sensitive data accessed');
});

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`Server running on port ${PORT}`);
});
```

When implementing rate limiting, it's crucial to provide clear feedback to clients (e.g., `429 Too Many Requests` status code with `Retry-After` header) and consider the appropriate limits based on the nature of your service and expected usage.
