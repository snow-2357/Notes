# 4.1 tRPC Fundamentals

tRPC (TypeScript Remote Procedure Call) is a framework that allows you to build end-to-end type-safe APIs without the need for traditional code generation or schema definition languages (like GraphQL SDL or OpenAPI/Swagger). It's designed specifically for TypeScript monorepos where your frontend and backend code share types.

## Why tRPC?
Traditional API development (REST, GraphQL) often involves:
*   Defining API endpoints/schemas (e.g., OpenAPI, GraphQL SDL).
*   Generating types for both frontend and backend based on these schemas.
*   Manual synchronization between frontend and backend contracts.

tRPC simplifies this significantly by leveraging TypeScript's type inference. When using tRPC in a monorepo, you write your backend procedures using TypeScript, and then your frontend automatically infers the types of inputs, outputs, and potential errors directly from those backend procedures. This means:
*   **End-to-End Type Safety:** Guarantees that your frontend calls your backend correctly and expects the right data types, catching errors at compile-time instead of runtime.
*   **Zero-Config Type Generation:** No manual schema definition or code generation steps. Types are inferred naturally.
*   **Blazing Fast Development:** Rapid iteration as type changes in the backend immediately reflect in the frontend without build steps.
*   **Minimal Bundle Size:** Only the necessary client-side code is bundled, not a large SDK.
*   **Developer Experience:** Autocompletion and immediate feedback in your IDE.

## Core Concepts:

1.  **Router:** The central piece of your tRPC backend. It's where you define your API procedures.
2.  **Procedures:** The actual API endpoints. tRPC procedures can be:
    *   **Queries:** For fetching data (read operations).
    *   **Mutations:** For modifying data (write operations).
    *   **Subscriptions:** For real-time data streams (like WebSockets).
3.  **Context:** An object that is accessible by all your procedures. It's typically used to carry information like the authenticated user, database connections, or other services. It's defined once and then passed to each procedure.
4.  **Transformers:** Used to serialize/deserialize data that is not JSON-compatible (e.g., `Date` objects, `BigInt`). SuperJSON is a common choice.
5.  **Type Inference:** The magic happens here. The tRPC client infers all the necessary types (input, output, errors) directly from the backend router's TypeScript definition.

## Basic Setup (Conceptual):

### 1. Backend (`server.ts`):

```typescript
// server.ts
import { initTRPC } from '@trpc/server';
import { z } from 'zod'; // For input validation

// Initialize tRPC
const t = initTRPC.context<Context>().create();

// Define your backend context
interface Context {
  // Add properties here that you want accessible in your procedures, e.g.,
  // userId?: string;
  // db: PrismaClient;
}

// You'd typically create a context factory in a real app
const createContext = () => ({}); // For simplicity, empty context

// Create a public procedure (no authentication needed)
const publicProcedure = t.procedure;

// Define your app router
export const appRouter = t.router({
  // Define a 'greeting' query
  greeting: publicProcedure
    .input(z.object({ name: z.string().optional() })) // Define input schema with Zod
    .query(({ input }) => {
      return `Hello ${input.name || 'world'}`;
    }),

  // Define a 'post' sub-router
  post: t.router({
    getById: publicProcedure
      .input(z.object({ id: z.string() }))
      .query(({ input }) => {
        // In a real app, you'd fetch from a DB
        return { id: input.id, title: `Post ${input.id}` };
      }),

    create: publicProcedure
      .input(z.object({ title: z.string(), content: z.string() }))
      .mutation(({ input }) => {
        // In a real app, you'd save to a DB
        console.log('Creating post:', input);
        return { id: String(Math.random()), ...input };
      }),
  }),
});

// Export type definition of API
export type AppRouter = typeof appRouter;

// --- Express/Node.js server setup (example) ---
import express from 'express';
import * as trpcExpress from '@trpc/server/adapters/express';

const app = express();
const PORT = 3000;

app.use(
  '/trpc', // Your tRPC endpoint
  trpcExpress.createExpressMiddleware({
    router: appRouter,
    createContext,
  })
);

app.listen(PORT, () => {
  console.log(`Server listening on port ${PORT}`);
  console.log(`tRPC endpoint: http://localhost:${PORT}/trpc`);
});
```

### 2. Frontend (`client.ts` or `App.tsx`):

```typescript
// client.ts or App.tsx (in your frontend project, sharing types with backend)
import { createTRPCProxyClient, httpBatchLink } from '@trpc/client';
import type { AppRouter } from '../server/server'; // Import the backend's AppRouter type!

// Create a tRPC client
const trpc = createTRPCProxyClient<AppRouter>({
  links: [
    httpBatchLink({
      url: 'http://localhost:3000/trpc', // URL of your backend tRPC endpoint
    }),
  ],
});

async function main() {
  // --- Query Example ---
  const greeting = await trpc.greeting.query({ name: 'tRPC user' });
  console.log('Greeting:', greeting); // "Hello tRPC user"

  // --- Sub-router Query Example ---
  const post = await trpc.post.getById.query({ id: '123' });
  console.log('Fetched Post:', post); // { id: '123', title: 'Post 123' }

  // --- Mutation Example ---
  const newPost = await trpc.post.create.mutate({
    title: 'My new tRPC post',
    content: 'This was created via a mutation!',
  });
  console.log('Created Post:', newPost); // { id: '...', title: 'My new tRPC post', content: '...' }

  // --- Type Safety in action ---
  // trpc.greeting.query({ names: 'invalid' }); // This would be a TypeScript error!
  // const invalidPost = await trpc.post.getById.query({ id: 123 }); // TypeScript error: expected string, got number
}

main();
```

## How Type Safety Works End-to-End:
The core idea is that the frontend client code *imports the `AppRouter` type* directly from the shared backend code. This allows the client-side `createTRPCProxyClient` to automatically generate a type-safe client that knows all the available procedures, their expected inputs, and their guaranteed outputs. Your IDE provides auto-completion, and TypeScript catches mismatches before runtime.

## Advantages:
*   **Unparalleled Developer Experience:** Real-time type checking and auto-completion.
*   **Reduced Boilerplate:** No schema syncing, less code to write and maintain.
*   **Increased Confidence:** Catch API errors at compile-time, not in production.
*   **Performance:** Batching of requests is built-in.
*   **Flexible:** Works with various adapters (Express, Next.js, Fastify, AWS Lambda, etc.)

## Limitations/Considerations:
*   **TypeScript Monorepo:** Most beneficial in a TypeScript monorepo where types can be shared directly. While it can be used without a monorepo, the type-sharing experience becomes slightly more complex.
*   **Not for Public APIs:** tRPC is typically for internal APIs where you control both the client and the server. For public-facing APIs, OpenAPI/GraphQL might be more suitable due to broader tooling and language-agnostic schema definitions.
*   **Learning Curve:** While simple in concept, understanding its nuances and integration can take a bit of time.

tRPC represents a modern approach to API development, offering significant productivity and reliability gains for TypeScript-centric applications. It's a strong contender for building full-stack applications where end-to-end type safety is a priority.
