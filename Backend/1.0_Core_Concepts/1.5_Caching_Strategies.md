# 1.5 Caching Strategies (Redis/In-memory)

Caching is a fundamental technique for improving the performance and scalability of backend applications. It involves storing frequently accessed data in a faster, more accessible location (the cache) so that future requests for that data can be served more quickly than retrieving it from its primary, slower storage (e.g., a database).

## Why Use Caching?
*   **Reduced Latency:** Data can be retrieved from a fast cache much quicker than from a database or external service.
*   **Reduced Database/API Load:** Less traffic hits your primary data sources, saving resources and potentially costs.
*   **Improved Scalability:** Your application can handle more requests with the same backend infrastructure.
*   **Better User Experience:** Faster response times lead to a more responsive application.

## Where to Cache:

1.  **Browser Cache (Client-side):** Storing data on the user's browser. Managed via HTTP headers (`Cache-Control`, `Expires`, `ETag`, `Last-Modified`).
2.  **CDN Cache (Edge/Distributed):** Content Delivery Networks cache static assets (images, CSS, JS) and sometimes dynamic content closer to the user.
3.  **Application Cache (Server-side):** Caching within your backend application.
    *   **In-Memory Cache:** Storing data directly in the application's RAM.
    *   **Distributed Cache:** Using a separate caching service (like Redis or Memcached) accessible by multiple application instances.
4.  **Database Cache:** Built-in caching mechanisms within databases (e.g., query caches).

This document focuses on **Application Cache**.

## Application Caching Strategies:

### 1. In-Memory Caching:

*   **How it works:** Data is stored directly within the application's process memory.
*   **Pros:** Extremely fast access (no network overhead). Simple to implement for single-instance applications.
*   **Cons:**
    *   **Not distributed:** Each application instance has its own cache. If data is updated in one instance, others might serve stale data.
    *   **Volatile:** Cache data is lost when the application restarts.
    *   **Limited by RAM:** Can only store as much data as the available memory of the application process.
    *   **Concurrency Issues:** Needs careful handling with locks if multiple threads/async operations modify the cache.
*   **Use cases:** Caching small, non-critical, or frequently changing data for a single application instance. Good for development or very simple services.

### 2. Distributed Caching (e.g., Redis, Memcached):

*   **How it works:** A separate, dedicated caching server or cluster manages the cache data. Application instances connect to this service.
*   **Pros:**
    *   **Distributed:** Cache is shared across multiple application instances, ensuring consistency.
    *   **Scalable:** Caching service can be scaled independently of the application.
    *   **Persistence (with Redis):** Redis can optionally persist data to disk, preventing complete loss on restart.
    *   **Rich Data Structures (with Redis):** Redis supports various data structures (strings, hashes, lists, sets, sorted sets), allowing for more complex caching patterns.
*   **Cons:**
    *   **Network Latency:** Involves network calls, which are slower than in-memory access (though still much faster than a database).
    *   **Complexity:** Requires managing a separate service.
*   **Use cases:** Most production-grade backend applications, microservices architectures, caching critical data that needs to be consistent across instances, user sessions, full-page caches.

## Common Caching Patterns:

1.  **Cache Aside (Lazy Loading):**
    *   **Read:** Application checks cache first. If data is found (cache hit), return it. If not (cache miss), fetch from DB, store in cache, then return.
    *   **Write:** Application writes to DB first, then invalidates/updates the cache.
    *   **Pros:** Simple, only caches data that is requested.
    *   **Cons:** Initial requests are slow (cache miss). Data might be slightly stale between write and cache invalidation.

2.  **Read Through:**
    *   **How it works:** Cache is in-line with the application. When data is requested, the cache library/service retrieves it from the underlying data source if it's not in the cache. The application only interacts with the cache.
    *   **Pros:** Simplifies application logic; cache manages data loading.
    *   **Cons:** Requires cache to "know" how to fetch from DB.

3.  **Write Through:**
    *   **How it works:** Application writes data to the cache, and the cache synchronously writes the data to the database.
    *   **Pros:** Data in cache is always consistent with the database.
    *   **Cons:** Write operations can be slower due to synchronous DB write.

4.  **Write Back (Write Behind):**
    *   **How it works:** Application writes data to the cache, and the cache asynchronously writes the data to the database later.
    *   **Pros:** Very fast write operations for the application.
    *   **Cons:** Data loss can occur if the cache crashes before data is written to DB. Cache consistency can be an issue.

## Cache Invalidation Strategies:

*   **Time-To-Live (TTL):** Data expires from the cache after a set period. Simple and effective for data that can tolerate some staleness.
*   **Least Recently Used (LRU):** When the cache is full, the least recently accessed items are removed to make space for new ones.
*   **Least Frequently Used (LFU):** Similar to LRU, but removes items that have been accessed the fewest times.
*   **Write-Through/Write-Back Invalidation:** Update/delete data in the cache when the underlying data source is modified.
*   **Event-Driven Invalidation:** Invalidate cache entries in response to specific events (e.g., a "product updated" event).

## Example with Node.js and Redis (`ioredis`):

```javascript
const express = require('express');
const Redis = require('ioredis');

const app = express();
const redis = new Redis(); // Connects to Redis on localhost:6379 by default

const USER_CACHE_KEY = 'user:';
const CACHE_TTL_SECONDS = 60 * 5; // 5 minutes

async function getUserFromDB(userId) {
  // Simulate a slow database call
  return new Promise(resolve => setTimeout(() => {
    console.log(`Fetching user ${userId} from DB...`);
    resolve({ id: userId, name: `User ${userId}`, email: `user${userId}@example.com` });
  }, 500));
}

app.get('/users/:id', async (req, res) => {
  const userId = req.params.id;
  const cacheKey = USER_CACHE_KEY + userId;

  try {
    // 1. Check cache first (Cache Aside pattern)
    const cachedUser = await redis.get(cacheKey);
    if (cachedUser) {
      console.log(`User ${userId} found in cache.`);
      return res.json(JSON.parse(cachedUser));
    }

    // 2. If not in cache, fetch from database
    const user = await getUserFromDB(userId);

    // 3. Store in cache and set TTL
    await redis.setex(cacheKey, CACHE_TTL_SECONDS, JSON.stringify(user));
    console.log(`User ${userId} fetched from DB and cached.`);

    res.json(user);
  } catch (error) {
    console.error('Error fetching user:', error);
    res.status(500).send('Internal Server Error');
  }
});

// Example endpoint to simulate updating a user and invalidating cache
app.put('/users/:id', async (req, res) => {
  const userId = req.params.id;
  const cacheKey = USER_CACHE_KEY + userId;

  // Simulate update in DB
  console.log(`Updating user ${userId} in DB...`);
  // await updateUserInDB(userId, req.body);

  // Invalidate cache
  await redis.del(cacheKey);
  console.log(`Cache for user ${userId} invalidated.`);

  res.status(200).send(`User ${userId} updated and cache invalidated.`);
});


const PORT = process.env.PORT || 3000;
app.listen(PORT, () => {
  console.log(`Server running on port ${PORT}`);
});
```
This example demonstrates a "Cache Aside" pattern for reading and a "Write Through/Invalidate" for writing, using Redis for distributed caching. Choose the right caching strategy based on your application's read/write patterns, data consistency requirements, and tolerance for stale data.
