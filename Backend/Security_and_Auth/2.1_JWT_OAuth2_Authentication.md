# 2.1 JWT/OAuth2 Authentication

Authentication and Authorization are critical components of nearly every backend application. They ensure that users are who they say they are (authentication) and that they have the necessary permissions to perform requested actions (authorization). This section will provide an overview of two common and powerful standards: JWT (JSON Web Tokens) and OAuth2.

## 2.1.1 JWT (JSON Web Tokens)

JWTs are an open standard (RFC 7519) that define a compact and self-contained way for securely transmitting information between parties as a JSON object. This information can be verified and trusted because it is digitally signed.

### Structure of a JWT:
A JWT typically consists of three parts, separated by dots (`.`):
`header.payload.signature`

1.  **Header:**
    *   Typically consists of two parts: the type of the token (JWT) and the signing algorithm being used (e.g., HMAC SHA256 or RSA).
    *   Example:
        ```json
        {
          "alg": "HS256",
          "typ": "JWT"
        }
        ```

2.  **Payload (Claims):**
    *   Contains the "claims" (statements) about an entity (typically, the user) and additional data.
    *   Claims are categorized as:
        *   **Registered claims:** Predefined, non-mandatory claims (e.g., `iss` (issuer), `exp` (expiration time), `sub` (subject), `aud` (audience)).
        *   **Public claims:** Custom claims that are publicly accessible.
        *   **Private claims:** Custom claims agreed upon by the parties, neither registered nor public.
    *   Example:
        ```json
        {
          "sub": "1234567890",
          "name": "John Doe",
          "admin": true,
          "iat": 1516239022 // Issued At
        }
        ```

3.  **Signature:**
    *   Created by taking the encoded header, the encoded payload, a secret key, and the algorithm specified in the header, and signing them.
    *   Used to verify that the sender of the JWT is who it says it is and to ensure that the message hasn't been changed along the way.

### How JWT Authentication Works:

1.  **User Login:** User sends credentials (username/password) to the authentication server.
2.  **Token Issuance:** Server verifies credentials, then creates a JWT with user-specific claims and signs it with a secret key.
3.  **Token Return:** The JWT is sent back to the client.
4.  **Client Stores Token:** Client typically stores the JWT in `localStorage`, `sessionStorage`, or an HTTP-only cookie.
5.  **API Requests:** For subsequent API requests, the client sends the JWT, usually in the `Authorization` header as a Bearer token: `Authorization: Bearer <token>`.
6.  **Server Verification:** The backend server extracts the JWT, verifies its signature using the secret key (ensuring authenticity and integrity), and decodes the payload to get user information.
7.  **Resource Access:** If the token is valid, the server grants access to the requested resource based on the claims (e.g., user roles, permissions).

### Pros:
*   **Stateless:** Server doesn't need to store session information (scalability).
*   **Compact:** Small size for efficient transmission.
*   **Self-contained:** Contains all necessary user information.
*   **Mobile-friendly:** Works well with mobile apps where cookies are less convenient.

### Cons:
*   **No Centralized Logout/Revocation:** Difficult to invalidate a token before its natural expiration. This can be mitigated with blacklisting or short token expiry times combined with refresh tokens.
*   **Security of Secret Key:** If the secret key is compromised, tokens can be forged.
*   **Token Size:** Can become large if too many claims are added, impacting request size.

## 2.1.2 OAuth2 (Open Authorization 2.0)

OAuth2 is an authorization framework that enables an application to obtain limited access to a user's protected resources on an HTTP service (e.g., Google, Facebook, GitHub). It is about delegated authorization, not authentication itself, though it's often used in conjunction with OpenID Connect for authentication.

### Key Roles:

1.  **Resource Owner:** The user who owns the protected resources (e.g., their photos on Google Photos).
2.  **Client:** The application that wants to access the resource owner's protected resources (e.g., a photo printing app).
3.  **Authorization Server:** The server that authenticates the resource owner and issues access tokens to the client (e.g., Google's authentication server).
4.  **Resource Server:** The server hosting the protected resources, capable of accepting and responding to protected resource requests using access tokens (e.g., Google Photos API).

### How OAuth2 Works (Authorization Code Grant Flow - most common for web apps):

1.  **Client Requests Authorization:** The client directs the user's browser to the Authorization Server's authorization endpoint. This request includes the client ID, requested scopes (permissions), and a redirect URI.
2.  **Resource Owner Authorizes:** The Authorization Server authenticates the user (if not already logged in) and asks if they grant the client the requested permissions.
3.  **Authorization Code Granted:** If the user approves, the Authorization Server redirects the user's browser back to the client's pre-registered Redirect URI, appending an Authorization Code.
4.  **Client Requests Access Token:** The client (from its backend) exchanges the Authorization Code with the Authorization Server's token endpoint. This request includes the Authorization Code, client ID, client secret, and redirect URI.
5.  **Access Token Granted:** The Authorization Server validates the code and client credentials, then issues an Access Token (and optionally a Refresh Token).
6.  **Client Accesses Resource:** The client uses the Access Token to make requests to the Resource Server (e.g., `Authorization: Bearer <access_token>`).
7.  **Resource Server Validates Token:** The Resource Server validates the Access Token and grants or denies access to the protected resource.

### Types of Grants (Flows):
OAuth2 defines several grant types for different client types and use cases:
*   **Authorization Code:** Most secure, used by confidential clients (web applications with a backend).
*   **Client Credentials:** For machine-to-machine authentication (no user involvement).
*   **Implicit (Deprecated):** Less secure, for public clients (single-page apps, mobile apps). Replaced by Authorization Code with PKCE.
*   **Resource Owner Password Credentials (Deprecated):** Highly discouraged, for trusted clients (e.g., first-party mobile apps).

### Pros:
*   **Delegated Authorization:** Users can grant limited access to their data without sharing their credentials.
*   **Widely Adopted:** Industry standard, well-understood.
*   **Flexible:** Supports various client types and use cases.
*   **Separation of Concerns:** Authentication handled by a dedicated server.

### Cons:
*   **Complexity:** Can be complex to implement correctly due to many moving parts and grant types.
*   **Authorization, Not Authentication:** By itself, OAuth2 only grants authorization. OpenID Connect is built on top of OAuth2 for authentication.

## JWT + OAuth2 Combination:
It's common to see OAuth2 used to *issue* JWTs as Access Tokens. In this scenario, the Authorization Server provides a JWT to the client as the Access Token. The Resource Server then validates this JWT directly, making for a very efficient authorization process. This combines the benefits of delegated authorization with stateless token verification.
