# 3.1 Pagination (Offset vs. Cursor)

Pagination is a technique used to divide a large set of data into smaller, manageable chunks (pages) for display or processing. It's essential for APIs that deal with large datasets, as returning all records at once can be slow, resource-intensive, and impractical.

## Why Use Pagination?
*   **Performance:** Reduces the amount of data transferred over the network and processed by both the server and client.
*   **Resource Management:** Prevents the server from being overwhelmed by requests for massive datasets.
*   **User Experience:** Improves application responsiveness and allows users to browse through data without long loading times.

## Types of Pagination:

### 1. Offset-based Pagination (Page-Number based)

This is the most common and intuitive method, often seen as "page 1 of 10." It uses `OFFSET` and `LIMIT` (or `SKIP` and `LIMIT` in some NoSQL databases) clauses in queries.

*   **Parameters:**
    *   `page` (or `pageNum`): The desired page number (e.g., 1, 2, 3...).
    *   `limit` (or `pageSize`): The number of items per page.

*   **How it works (SQL Example):**
    ```sql
    SELECT * FROM items
    ORDER BY created_at DESC
    LIMIT :limit OFFSET (:page - 1) * :limit;
    ```
    If `page = 1` and `limit = 10`, it fetches items 1-10.
    If `page = 2` and `limit = 10`, it fetches items 11-20.

*   **Pros:**
    *   Easy to implement and understand.
    *   Allows direct navigation to any page number.
    *   Can show total page count.

*   **Cons:**
    *   **Performance Degradation:** As the `OFFSET` value increases, the database still has to scan (or even retrieve) all preceding rows before it can get to the desired offset. This can become very slow for large offsets.
    *   **Inconsistency/Duplicates/Missed Items (with changing data):** If items are added or deleted while a user is paginating, the offset can shift. A user viewing page 2 might see duplicates from page 1 or miss some items entirely. This is a significant issue for frequently updated data.

*   **Best for:**
    *   Small to medium datasets.
    *   When data is mostly static or changes infrequently.
    *   When showing a total page count or direct page navigation is a strong requirement.

### 2. Cursor-based Pagination (Keyset/Seek Pagination)

This method uses a "cursor" (usually a unique, sequential, and immutable value from the last item of the previous page, like an ID or a timestamp) to determine the starting point of the next page. It's often seen as "Load More" or "Next/Previous."

*   **Parameters:**
    *   `limit` (or `pageSize`): Number of items to return.
    *   `after` (or `cursor`): The value of a specific field (e.g., `id`, `created_at`) from the last item of the *previous* page.

*   **How it works (SQL Example):**
    ```sql
    SELECT * FROM items
    WHERE id > :afterCursor -- or created_at < :afterCursor for descending
    ORDER BY id ASC
    LIMIT :limit;
    ```
    To get the next page, the client provides the `id` of the last item received.

*   **Pros:**
    *   **Excellent Performance:** The database can directly seek to the starting point, making it highly efficient even for very large datasets and deep pagination. No full table scans.
    *   **Stable Results:** Because it relies on the position relative to a specific item, adding or deleting items *before* the cursor won't affect the results of subsequent pages.
    *   **Scales better** with large data volumes.

*   **Cons:**
    *   **No Direct Page Navigation:** You cannot jump to page 5 directly. You can only go "next" or "previous" from a given cursor.
    *   **No Total Page Count:** You generally cannot easily determine the total number of pages without a separate, potentially expensive, query.
    *   **Requires Sorted Data:** The column used for the cursor (`id`, `created_at`) must be unique and consistently sortable.

*   **Best for:**
    *   Large, frequently updated datasets (e.g., social media feeds).
    *   When performance and consistency across dynamic data are critical.
    *   "Infinite scrolling" or "Load More" UIs.

## Implementing Pagination in an API:

### API Design Considerations:

*   **Consistent Parameters:** Use consistent naming for pagination parameters (`page`, `limit`, `after`, `cursor`).
*   **Default Values:** Provide sensible default `limit` values to protect your API.
*   **Max Limit:** Set a maximum `limit` to prevent clients from requesting excessively large pages.
*   **Return Metadata:** Include pagination metadata in the API response (e.g., total records, total pages, current page, next cursor).

### Example with Node.js/Express (Offset-based):

```javascript
const express = require('express');
const app = express();
const items = Array.from({ length: 100 }, (_, i) => ({ id: i + 1, name: `Item ${i + 1}`, createdAt: new Date() }));

app.get('/api/items_offset', (req, res) => {
  const page = parseInt(req.query.page) || 1;
  const limit = parseInt(req.query.limit) || 10;
  const startIndex = (page - 1) * limit;
  const endIndex = page * limit;

  const results = {};

  if (endIndex < items.length) {
    results.next = {
      page: page + 1,
      limit: limit
    };
  }

  if (startIndex > 0) {
    results.previous = {
      page: page - 1,
      limit: limit
    };
  }

  results.totalItems = items.length;
  results.totalPages = Math.ceil(items.length / limit);
  results.currentPage = page;
  results.pageSize = limit;
  results.data = items.slice(startIndex, endIndex);

  res.json(results);
});

// Example with Node.js/Express (Cursor-based) - simplified for conceptual understanding
app.get('/api/items_cursor', (req, res) => {
  const limit = parseInt(req.query.limit) || 10;
  const after = parseInt(req.query.after) || 0; // The ID of the last item from previous page

  // Sort by ID to ensure consistent order
  const sortedItems = [...items].sort((a, b) => a.id - b.id);

  // Find the index after the cursor
  let startIndex = 0;
  if (after > 0) {
    const cursorIndex = sortedItems.findIndex(item => item.id === after);
    if (cursorIndex !== -1) {
      startIndex = cursorIndex + 1;
    } else {
      // Cursor not found, perhaps invalid or item was deleted
      return res.status(400).json({ error: 'Invalid cursor' });
    }
  }

  const data = sortedItems.slice(startIndex, startIndex + limit);
  const nextCursor = data.length > 0 ? data[data.length - 1].id : null;

  res.json({
    data,
    nextCursor,
    hasMore: (startIndex + data.length) < sortedItems.length
  });
});


const PORT = process.env.PORT || 3000;
app.listen(PORT, () => console.log(`Server running on port ${PORT}`));
```

Choosing between offset and cursor-based pagination depends heavily on your data characteristics, performance requirements, and user experience goals. Cursor-based is generally preferred for large, dynamic datasets.
