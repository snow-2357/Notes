# 3.5 MongoDB Schema Design

MongoDB is a NoSQL, document-oriented database. Unlike relational databases that use tables, rows, and predefined schemas, MongoDB stores data in flexible, JSON-like documents called BSON. This schema flexibility is a powerful feature, but designing an effective schema is crucial for performance, scalability, and maintainability.

## Key Principles of MongoDB Schema Design:

1.  **Denormalization (Embedding) vs. Normalization (Referencing):**
    *   This is the most critical decision in MongoDB schema design.

    ### Embedding:
    *   **Concept:** Store related data in a single document. (e.g., embedding comments directly within a `post` document).
    *   **Pros:**
        *   **Better Read Performance:** Fewer queries required (single query retrieves all related data).
        *   **Atomic Operations:** Updates to embedded documents are atomic (for a single document).
        *   **Simpler Application Code:** Less need for joins or multiple database calls.
        *   **Fewer Joins:** Reduces the need for `$lookup` (MongoDB's equivalent of joins).
    *   **Cons:**
        *   **Document Size Limit:** MongoDB documents have a 16MB size limit. Very large embedded arrays can hit this limit.
        *   **Duplication (sometimes):** If embedded data is referenced elsewhere, it might be duplicated, leading to update anomalies if not managed carefully.
        *   **Update Complexity (sometimes):** If only a small part of a large embedded array needs updating, the entire document might need to be rewritten.
    *   **When to Use:**
        *   One-to-one relationships where data is frequently accessed together.
        *   One-to-many relationships where the "many" side is relatively small and embedded documents are often read with the parent (e.g., comments on a blog post, line items in an order).

    ### Referencing:
    *   **Concept:** Store related data in separate documents and link them using references (e.g., storing `post_id` in a `comment` document). Similar to foreign keys in relational databases.
    *   **Pros:**
        *   **Avoids Document Size Limit:** Can store virtually unlimited related data.
        *   **Reduced Duplication:** Data is stored once, reducing update anomalies.
        *   **More Flexible Relationships:** Supports many-to-many relationships naturally.
    *   **Cons:**
        *   **More Queries:** Requires multiple queries (`$lookup` or application-level joins) to retrieve all related data, impacting read performance.
        *   **Not Atomic:** Operations across multiple documents are not atomic by default (require transactions in newer MongoDB versions).
    *   **When to Use:**
        *   One-to-many relationships where the "many" side is large or unbound (e.g., users and their orders - a user can have many orders).
        *   Many-to-many relationships.
        *   When data needs to be accessed independently of its parent.
        *   When you need to avoid hitting the 16MB document size limit.

2.  **Schema on Write vs. Schema on Read:**
    *   **Schema on Read (Flexible Schema):** MongoDB allows documents in a collection to have different structures. This offers great flexibility during development.
    *   **Best Practice:** While flexible, it's good practice to enforce a "logical schema" or "implicit schema." Most documents in a collection should have a similar structure. Use schema validation or application-level validation to ensure data consistency.

3.  **Data Types:**
    *   Use appropriate BSON data types (e.g., `ObjectId` for IDs, `Date` for dates, `NumberLong` for large integers).
    *   Using the correct data type helps with efficient storage and querying.

4.  **Field Naming:**
    *   Use clear, descriptive, and consistent field names (e.g., `camelCase` or `snake_case`).
    *   Shorter field names reduce document size, which can be beneficial for large collections.

5.  **Small Arrays/Large Arrays:**
    *   For small, fixed-size arrays that are always read with the parent, embedding is fine.
    *   For very large, unbounded arrays (e.g., `user.followers`), consider referencing or a separate collection to avoid the 16MB document limit and improve update performance.

6.  **`_id` Field:**
    *   Every MongoDB document requires an `_id` field. If not provided, MongoDB automatically generates an `ObjectId`.
    *   `ObjectId` is a good default as it's small, unique, and automatically indexed.
    *   You can use other data types for `_id` (e.g., UUIDs, application-specific IDs) but ensure they are unique and indexed.

7.  **Data Versioning:**
    *   For documents that change frequently and you need to track history, consider embedding a version number or an array of historical changes.

## Practical Examples:

### Blog Posts and Comments:

*   **Embedding (for small number of comments):**
    ```json
    {
      "_id": ObjectId("..."),
      "title": "My Blog Post",
      "content": "...",
      "author": "John Doe",
      "comments": [
        { "user": "Alice", "text": "Great post!", "date": ISODate("...") },
        { "user": "Bob", "text": "Learned a lot.", "date": ISODate("...") }
      ]
    }
    ```
    *   **Reasoning:** Comments are usually retrieved with the post, and a single post is unlikely to have millions of comments.

*   **Referencing (for many comments, or if comments need independent access):**
    ```json
    // posts collection
    {
      "_id": ObjectId("post123"),
      "title": "My Blog Post",
      "content": "...",
      "author": "John Doe"
    }

    // comments collection
    {
      "_id": ObjectId("comment456"),
      "post_id": ObjectId("post123"),
      "user": "Alice",
      "text": "Great post!",
      "date": ISODate("...")
    }
    ```
    *   **Reasoning:** If comments are very numerous, or if you need to query comments independently (e.g., "show all comments by Alice"), referencing is better. Use `$lookup` to join.

### Orders and Order Items:

*   **Embedding (typical for order items):**
    ```json
    {
      "_id": ObjectId("order123"),
      "customer_id": ObjectId("cust789"),
      "order_date": ISODate("..."),
      "total_amount": 99.99,
      "items": [
        { "product_id": ObjectId("prodA"), "name": "Laptop", "qty": 1, "price": 800.00 },
        { "product_id": ObjectId("prodB"), "name": "Mouse", "qty": 1, "price": 19.99 }
      ],
      "status": "completed"
    }
    ```
    *   **Reasoning:** Order items are intrinsically part of an order and are almost always accessed together. The `items` array is usually not extremely large.

## Schema Validation:
Despite its flexible schema, MongoDB supports schema validation since version 3.2. You can define validation rules for collections using JSON Schema. This ensures that documents inserted or updated conform to a predefined structure, helping maintain data consistency.

```javascript
db.createCollection("users", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["name", "email", "age"],
      properties: {
        name: {
          bsonType: "string",
          description: "must be a string and is required"
        },
        email: {
          bsonType: "string",
          pattern: "^.+@.+$",
          description: "must be a valid email address and is required"
        },
        age: {
          bsonType: "int",
          minimum: 18,
          maximum: 120,
          description: "must be an integer in [18, 120] and is required"
        }
      }
    }
  },
  validationAction: "error" // 'error' (default) or 'warn'
})
```

Effective MongoDB schema design balances the benefits of embedding (read performance, atomicity) with the necessity of referencing (avoiding document size limits, managing large arrays, reducing duplication). The best approach depends heavily on your application's specific data access patterns and requirements.
