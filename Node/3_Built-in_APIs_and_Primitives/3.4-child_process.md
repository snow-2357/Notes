# 3.4 `child_process`

The `child_process` module in Node.js allows you to spawn new processes that run external commands or scripts. This provides a powerful way to interact with the operating system, execute other programs, or delegate computationally intensive tasks to separate processes, thereby avoiding blocking the Node.js event loop.

## What is `child_process`?

Node.js itself runs as a single process, and its JavaScript execution is single-threaded. However, modern operating systems are multi-process, and often you need to interact with other programs (like `git`, `ffmpeg`, `python`, or even other Node.js scripts). The `child_process` module enables this by allowing you to create "child" processes.

## Why Use `child_process`?

-   **Execute System Commands:** Run any command-line utility or script available on the OS.
-   **Leverage Multi-core CPUs (indirectly):** By offloading heavy computations or long-running tasks to entirely separate processes, the main Node.js application remains responsive. This is distinct from `worker_threads` which runs JavaScript in multiple threads within *one* Node.js process.
-   **Integrate with Other Languages:** Run scripts written in Python, Ruby, Java, etc., and interact with their output.
-   **Background Tasks:** Initiate tasks that run independently in the background.

## Difference from `worker_threads`

It's important to differentiate `child_process` from `worker_threads`:

| Feature            | `child_process`                               | `worker_threads`                                     |
| :----------------- | :-------------------------------------------- | :--------------------------------------------------- |
| **Isolation**      | Separate OS processes                         | Threads within the same Node.js process              |
| **Memory Sharing** | No shared memory                              | Can share `SharedArrayBuffer`                        |
| **Communication**  | IPC (pipes, stdio), `send()`/`'message'`      | Message passing (`postMessage()`)                    |
| **Primary Use**    | Running external programs (Node.js or other), background tasks | CPU-bound JavaScript tasks                           |
| **Overhead**       | Higher (full OS process)                      | Lower (thread creation)                              |

## Methods for Spawning Child Processes

The `child_process` module provides four primary functions for creating child processes, each suited for different use cases:

### 1. `spawn(command[, args][, options])`

-   **Concept:** Spawns a new process directly without spawning a shell. This is the most efficient and recommended method for running external processes.
-   **Behavior:** Returns a `ChildProcess` object. The `stdout`, `stdin`, and `stderr` of the child process are made available as streams, allowing you to interact with data in a non-blocking, streaming fashion.
-   **Use Case:** Ideal for long-running processes, when handling large amounts of data streamingly, or when more control over the process is needed. It's more secure as it avoids shell interpretation.

```javascript
const { spawn } = require('child_process');

const ls = spawn('ls', ['-lh', '/usr']); // Example: listing directory contents

ls.stdout.on('data', (data) => {
  console.log(`stdout: ${data}`);
});

ls.stderr.on('data', (data) => {
  console.error(`stderr: ${data}`);
});

ls.on('close', (code) => {
  console.log(`child process exited with code ${code}`);
});

ls.on('error', (err) => {
  console.error('Failed to start child process.', err);
});
```

### 2. `exec(command[, options][, callback])`

-   **Concept:** Spawns a shell and runs a command inside that shell.
-   **Behavior:** Buffers the entire `stdout` and `stderr` output and passes them to a callback function once the process terminates. It's blocking from the perspective of the child process's output until it completes, but the `exec` call itself is non-blocking to the Node.js event loop.
-   **Use Case:** Simple shell commands that produce relatively small output. Convenient for commands that rely on shell features (like piping or globbing).
-   **Security Concern:** Vulnerable to shell injection if user input is directly included in `command`.

```javascript
const { exec } = require('child_process');

exec('grep "Error" *.log', (error, stdout, stderr) => {
  if (error) {
    console.error(`exec error: ${error}`);
    return;
  }
  console.log(`stdout: ${stdout}`);
  console.error(`stderr: ${stderr}`);
});
```

### 3. `execFile(file[, args][, options][, callback])`

-   **Concept:** Similar to `exec()`, but spawns the process directly without a shell, like `spawn()`.
-   **Behavior:** Buffers `stdout` and `stderr` and passes them to a callback.
-   **Use Case:** Running executable files directly. It's safer than `exec()` because it avoids shell interpretation, making it immune to shell injection vulnerabilities.

```javascript
const { execFile } = require('child_process');

execFile('node', ['--version'], (error, stdout, stderr) => {
  if (error) {
    throw error;
  }
  console.log(stdout); // vX.Y.Z
});
```

### 4. `fork(modulePath[, args][, options])`

-   **Concept:** A special case of `spawn()` that specifically spawns new Node.js processes.
-   **Behavior:** Creates a persistent IPC (Inter-Process Communication) channel between the parent and child processes, allowing messages to be passed back and forth using `process.send()` and the `message` event.
-   **Use Case:** Spawning multiple Node.js instances to leverage multi-core systems, often used in conjunction with the `cluster` module. This is ideal for offloading long-running, CPU-bound JavaScript tasks to a separate Node.js process without the overhead of manually managing IPC channels.

```javascript
// parent.js
const { fork } = require('child_process');
const child = fork('child.js');

child.on('message', (msg) => {
  console.log('Message from child:', msg); // Message from child: { hello: 'parent' }
});

child.send({ hello: 'child' }); // Send a message to the child process

// child.js
process.on('message', (msg) => {
  console.log('Message from parent:', msg); // Message from parent: { hello: 'child' }
  process.send({ hello: 'parent' }); // Send a message back to the parent
});
```

## Inter-Process Communication (IPC)

-   **`message` event and `send()` method:** Used for structured data exchange specifically with `fork()`. Data is JSON-serialized.
-   **Standard I/O Streams:** `child.stdout.pipe(process.stdout)`, `process.stdin.pipe(child.stdin)` can be used with `spawn()` to stream data directly.

## Events

`ChildProcess` objects are `EventEmitter` instances and emit several important events:
-   **`close`**: Emitted when the stdio streams of a child process have been closed.
-   **`exit`**: Emitted when the child process exits. Provides the exit `code` and `signal`.
-   **`error`**: Emitted if the process could not be spawned or killed.
-   **`message`**: (For `fork()` and IPC-enabled `spawn()`) Emitted when a message is received from the child process.

## Considerations

-   **Security:** Be extremely cautious when using `exec()` or passing user-controlled input to any `child_process` method, as it can lead to **shell injection vulnerabilities**. Always prefer `spawn()` or `execFile()` with arguments provided as an array to avoid this.
-   **Performance:** Spawning a new OS process is resource-intensive. Use `child_process` judiciously.
-   **Error Handling:** Always include robust error handling (`.on('error')`, `try/catch` with callbacks) to manage failures gracefully.

The `child_process` module is an indispensable tool for Node.js developers, enabling powerful integration with the underlying operating system and external programs.
