# 3.3 The `cluster` Module

Node.js, by default, runs on a single thread. This means a single Node.js process can only utilize one CPU core, which can be a bottleneck for CPU-intensive tasks or high-traffic network applications on multi-core servers. The `cluster` module provides a way to overcome this limitation by allowing you to easily create child processes (workers) that share server ports, effectively leveraging all available CPU cores.

## What is the `cluster` Module?

The `cluster` module enables a single Node.js application to spawn multiple child processes, called "workers," which can then share the same server port. This allows the application to distribute incoming client connections across these workers, harnessing the power of multi-core CPUs and significantly improving the application's throughput and resilience.

## How `cluster` Works

The `cluster` module operates on a **master-worker architecture**:

1.  **Master Process (Primary):**
    *   When you start a Node.js application using `cluster`, the first process to run is the master (or primary) process.
    *   Its primary role is to manage the worker processes. It forks new workers, monitors their status, and can restart them if they die.
    *   It's responsible for setting up the server socket and, by default, distributes incoming connections to the workers using a round-robin algorithm. This ensures load balancing.
    *   The master process typically does not handle any direct client requests itself; its main job is orchestration.

2.  **Worker Processes (Secondary):**
    *   These are full Node.js processes, each with its own V8 instance, event loop, and memory space.
    *   They are spawned by the master process using `child_process.fork()`.
    *   Workers can bind to the same network port as the master (via `server.listen()` in workers) because the master process is designed to distribute the connections.
    *   Each worker handles client requests independently.

3.  **Inter-Process Communication (IPC):**
    *   The master and worker processes communicate via an IPC channel (a pipe). This allows them to send messages back and forth, enabling the master to manage workers and workers to report their status or send data.

## Creating a Cluster Example

```javascript
const cluster = require('cluster');
const http = require('http');
const numCPUs = require('os').cpus().length;

if (cluster.isMaster) { // Node.js v16+ uses cluster.isPrimary
  console.log(`Master ${process.pid} is running`);

  // Fork workers for each CPU core
  for (let i = 0; i < numCPUs; i++) {
    cluster.fork();
  }

  cluster.on('exit', (worker, code, signal) => {
    console.log(`Worker ${worker.process.pid} died with code ${code}, signal ${signal}`);
    // Optional: Respawn worker
    console.log('Forking a new worker...');
    cluster.fork();
  });

  cluster.on('online', (worker) => {
    console.log(`Worker ${worker.process.pid} is online`);
  });

} else {
  // Workers can share any TCP connection.
  // In this case, it is an HTTP server.
  http.createServer((req, res) => {
    // Simulate some work
    let sum = 0;
    for (let i = 0; i < 1e7; i++) { // A small CPU-bound task
        sum += i;
    }
    res.writeHead(200);
    res.end(`Hello from worker ${process.pid}! Sum: ${sum}\n`);
  }).listen(8000);

  console.log(`Worker ${process.pid} started`);
}
```
To run this example, save it as `cluster-app.js` and execute `node cluster-app.js`. Then, open your browser to `http://localhost:8000` or use `curl http://localhost:8000` multiple times. You will see different worker PIDs responding, demonstrating load distribution.

## Master-Worker Communication

The master and worker processes can communicate using the `worker.send()` method (from master to worker) and `process.send()` (from worker to master), along with listening for the `'message'` event.

```javascript
// ... inside master process
cluster.on('fork', (worker) => {
  worker.send('Hello from master to worker ' + worker.process.pid);
});

// ... inside worker process
process.on('message', (msg) => {
  console.log(`Worker ${process.pid} received: ${msg}`);
  process.send(`Worker ${process.pid} acknowledges: "${msg}"`);
});
```

## Zero-Downtime Restarts/Reloads

The `cluster` module can facilitate updating your application code without dropping active connections. You can implement logic in the master process to:
1.  Fork new workers running the new code.
2.  Once new workers are online and ready, gracefully shut down old workers (e.g., by telling them to stop accepting new connections and finish existing ones).
This allows for seamless deployments and updates.

## Differences and Relationship with Other Concurrency Modules

-   **`cluster` vs. `child_process`:** The `cluster` module is built on top of `child_process.fork()`. While `child_process` can spawn any external process, `cluster` specifically focuses on spawning Node.js workers to share a common server port for load balancing and managing their lifecycle.

-   **`cluster` vs. `worker_threads`:**
    *   **`cluster`:** Provides process-level parallelism. Each worker is a separate Node.js process. Best for **network-bound** applications (e.g., web servers) that benefit from distributing I/O load across CPU cores. Memory is not shared directly.
    *   **`worker_threads`:** Provides thread-level parallelism. Workers are threads within a single Node.js process. Best for **CPU-bound** JavaScript tasks (e.g., heavy computations) that would otherwise block the Event Loop. Can share memory (`SharedArrayBuffer`).

    It's possible, and sometimes beneficial, to use them together: a `cluster` worker (a single Node.js process) could itself spawn `worker_threads` to handle its internal CPU-intensive tasks.

## Considerations

-   **Memory Consumption:** Each worker process is a full Node.js instance, meaning it has its own V8 engine, Event Loop, and memory. This increases the total memory footprint of the application.
-   **IPC Overhead:** Communication between master and workers (or between workers themselves) incurs IPC overhead, so excessive messaging should be avoided.
-   **State Management:** Since workers don't share memory, managing application state (e.g., user sessions, in-memory caches) across multiple workers requires external solutions (e.g., Redis, database) or "sticky sessions" (where a client always connects to the same worker).
-   **Application Logic:** The application logic inside each worker must be designed to be stateless or handle distributed state correctly.

The `cluster` module is an essential tool for building scalable and fault-tolerant Node.js server applications, allowing them to fully utilize modern multi-core server hardware.
