# 2.1 Module Systems

Module systems are crucial for organizing, encapsulating, and reusing code in larger applications. They allow developers to break down complex programs into smaller, manageable, and self-contained units, each with its own scope, exporting only what's necessary and importing what it needs from other modules.

Node.js primarily supports two module systems: **CommonJS (CJS)**, its original module system, and **ECMAScript Modules (ESM)**, the official standard for JavaScript.

## CommonJS (CJS)

CommonJS was the pioneering module system for server-side JavaScript environments, notably Node.js. It's designed for synchronous loading of modules, which makes sense in a server environment where files are typically local.

**Syntax:**
-   **Exporting:** Use `module.exports` or `exports` to define what a module makes available to others.
    ```javascript
    // myModule.js
    function add(a, b) {
      return a + b;
    }

    const PI = 3.14159;

    module.exports = { // Exporting an object
      add,
      PI
    };

    // Or export individually
    // exports.add = add;
    // exports.PI = PI;
    ```
-   **Importing:** Use the `require()` function to import modules.
    ```javascript
    // main.js
    const { add, PI } = require('./myModule'); // Destructuring assignment
    // const myModule = require('./myModule'); // Importing the whole object

    console.log(add(2, 3)); // 5
    console.log(PI);        // 3.14159
    ```

**Behavior:**
-   **Synchronous Loading:** `require()` loads modules synchronously. Execution pauses until the required module is fully loaded and processed. This is generally fine for local file system access but can be a bottleneck for remote resources (which `require` isn't designed for).
-   **Caching:** Modules are loaded and executed only once. Subsequent `require()` calls for the same module return the cached instance, preventing redundant execution and ensuring singletons (e.g., database connections).
-   **Exports are Copies (for primitives):** When a module exports a primitive value (like a number, string), a copy of that value is exported. Changes to the value within the exporting module won't reflect in the importing module after the initial export. For objects, a reference is exported.
-   **`this` Context:** In a CommonJS module, `this` refers to `module.exports` (or an empty object if nothing is explicitly exported).

**When to Use:**
-   Existing Node.js projects that primarily use CommonJS.
-   Utility scripts or CLIs where synchronous loading isn't an issue.

## ECMAScript Modules (ESM)

ECMAScript Modules are the official standard module system for JavaScript, designed for both browser and Node.js environments. They offer static analysis capabilities, which are crucial for tooling like tree-shaking (removing unused code).

**Syntax:**
-   **Exporting:** Use `export` keyword.
    ```javascript
    // myModule.mjs or myModule.js (with "type": "module" in package.json)
    export function subtract(a, b) {
      return a - b;
    }

    export const GREETING = "Hello, ESM!";

    // Default export (one per module)
    export default class MyClass { /* ... */ }
    ```
-   **Importing:** Use `import` keyword.
    ```javascript
    // main.mjs or main.js (with "type": "module" in package.json)
    import { subtract, GREETING } from './myModule.js';
    import MyClass from './myModule.js'; // For default export

    console.log(subtract(5, 2)); // 3
    console.log(GREETING);       // Hello, ESM!
    const instance = new MyClass();
    ```

**Behavior:**
-   **Asynchronous Loading (Conceptually):** While ESM can be loaded synchronously in Node.js for local files, the underlying specification is designed for asynchronous, non-blocking loading (which is essential for browsers).
-   **Static Analysis:** The `import`/`export` syntax is static; dependencies can be determined without executing the code. This enables advanced tooling optimizations like tree-shaking.
-   **Exports are Live Bindings:** ESM exports are live references to the values in the exporting module. If an exported variable's value changes in the exporting module, the importing module will see the updated value.
-   **Top-Level `await`:** ESM modules allow `await` at the top level of a module, outside of an `async` function. This enables modules to pause their own initialization until a Promise resolves.
-   **Strict Mode:** ESM modules automatically run in strict mode.

**How to Enable in Node.js:**
Node.js provides two ways to use ESM:
1.  **File Extension:** Use the `.mjs` file extension for your module files. Node.js treats `.mjs` files as ESM by default.
2.  **`package.json` `"type": "module"`:** In your `package.json`, set `"type": "module"`. This makes all `.js` files in that package (and its subdirectories, unless overridden) be treated as ESM. You can then use `.cjs` for CommonJS files within that package.

**When to Use:**
-   New Node.js projects.
-   When sharing code between Node.js and browser environments.
-   When leveraging tooling that benefits from static module analysis (e.g., Webpack, Rollup for tree-shaking).

## Interoperability

Node.js has mechanisms to handle both module systems, but with some rules:

-   **ESM can `import` CJS:** An ESM module can import a CommonJS module using the `import` syntax. The imported CommonJS module's `module.exports` object becomes the default export of the imported module.
    ```javascript
    // cjsModule.cjs
    module.exports = {
      name: "CJS Module"
    };

    // esmModule.mjs
    import cjsModule from './cjsModule.cjs';
    console.log(cjsModule.name); // CJS Module
    ```
-   **CJS cannot directly `require()` ESM:** A CommonJS module cannot directly `require()` an ESM module. Attempting to do so will result in an error. If a CommonJS module needs to use an ESM module, it often requires dynamic `import()` within an `async` function.
    ```javascript
    // esmModule.mjs
    export const esmValue = "I am ESM";

    // cjsModule.cjs
    // const esmModule = require('./esmModule.mjs'); // ERROR!
    // console.log(esmModule.esmValue);

    // Correct way (dynamic import)
    async function loadEsm() {
      const esmModule = await import('./esmModule.mjs');
      console.log(esmModule.esmValue); // I am ESM
    }
    loadEsm();
    ```

## Comparison Table

| Feature          | CommonJS (CJS)                                   | ECMAScript Modules (ESM)                                |
| :--------------- | :----------------------------------------------- | :------------------------------------------------------ |
| **Syntax**       | `require()`, `module.exports`, `exports`         | `import`, `export`, `export default`                    |
| **Loading**      | Synchronous                                      | Asynchronous (conceptually), but often synchronous in Node.js for local files |
| **Binding**      | Exports are copies (for primitives)              | Exports are live bindings (references)                  |
| **`this`**       | Refers to `module.exports`                       | `undefined` at the top level                            |
| **Strict Mode**  | Not by default                                   | Always in strict mode                                   |
| **Top-Level `await`** | No                                               | Yes                                                     |
| **Filename Extension** | `.js` (default if `"type"` not specified) | `.mjs`, or `.js` with `"type": "module"`                |
| **Interop**      | Cannot `require()` ESM directly                  | Can `import` CJS (default export)                       |
| **Static Analysis** | Limited                                          | Full (enables tree-shaking)                             |

Choosing between CJS and ESM depends on the project context, but for new Node.js development, ESM is generally recommended due to its standardization, static analysis benefits, and cleaner syntax.
