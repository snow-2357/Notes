
# 1.3 Back-of-the-envelope Estimation

Back-of-the-envelope estimation is the practice of making quick, approximate calculations to understand the scale of a system. In a system design interview, these estimations are crucial for scoping the problem, identifying potential bottlenecks, and justifying your design choices.

## 1. Introduction

**Why is it important?**

*   **Scoping:** Helps you understand if you're designing a system for thousands of users or hundreds of millions.
*   **Identifying Constraints:** Highlights potential challenges early on (e.g., "We'll need a lot of storage," or "The write QPS is very high").
*   **Justifying Design Choices:** Your estimations provide a quantitative basis for your architectural decisions (e.g., "Given the high read QPS, a caching layer is essential").

## 2. Key Numbers to Know

Having a rough idea of these numbers is incredibly helpful for quick calculations.

### Powers of 2

| Power | Value      | Approx. | Unit        |
| :---- | :--------- | :------ | :---------- |
| 2^10  | 1,024      | 1 K     | Kilo        |
| 2^20  | 1,048,576  | 1 M     | Mega        |
| 2^30  | 1,073,741,824 | 1 G     | Giga        |
| 2^40  | ...        | 1 T     | Tera        |

### Common Latency Numbers

| Action                               | Latency        |
| :----------------------------------- | :------------- |
| L1 cache reference                   | ~1 ns          |
| L2 cache reference                   | ~5 ns          |
| Main memory reference                | ~100 ns        |
| Send 1 KB over 1 Gbps network        | ~10,000 ns (10 µs) |
| Read 1 MB from memory                | ~250,000 ns (250 µs) |
| Round trip within same datacenter    | ~500,000 ns (500 µs) |
| Read 1 MB from SSD                   | ~1,000,000 ns (1 ms) |
| Round trip CA to Netherlands         | ~150,000,000 ns (150 ms) |

### Availability Numbers ("Nines")

| Availability | Downtime per year |
| :----------- | :---------------- |
| 99%          | ~3.65 days        |
| 99.9%        | ~8.77 hours       |
| 99.99%       | ~52.6 minutes     |
| 99.999%      | ~5.26 minutes     |

## 3. How to Approach Estimations

1.  **Clarify and State Assumptions:** Always start by stating the assumptions you are making. There's no single right answer, so your assumptions set the context for your calculations.
2.  **Start with High-Level Numbers:** Typically, you'll start with user numbers like Daily Active Users (DAU) or Monthly Active Users (MAU).
3.  **Break Down the Problem:**

    *   **Traffic/QPS (Queries Per Second) Estimation:**
        *   Start with DAU.
        *   Estimate the number of actions per user per day (e.g., 5 posts, 100 reads).
        *   Calculate total daily actions.
        *   Divide by the number of seconds in a day (approx. 86,400, often rounded to 100,000 for simplicity) to get average QPS.
        *   Consider peak load (often 2-4x the average).

    *   **Storage Estimation:**
        *   Estimate the size of a single data entity (e.g., one post, one image).
        *   Estimate the number of new entities per day.
        *   Multiply to get daily storage increase.
        *   Multiply by the number of days in the desired period (e.g., 5 years) to get total storage.

    *   **Bandwidth Estimation:**
        *   Estimate the size of data transferred per request (ingress/egress).
        *   Multiply by the QPS to get the required bandwidth.

4.  **Use Approximations and Rounding:** Don't get bogged down in precise calculations. Round numbers to make the math easier (e.g., 86,400 seconds/day ≈ 10^5 seconds/day).

## 4. Example Estimation: A Simple Twitter Clone

**Assumptions:**

*   100 million Daily Active Users (DAU).
*   Each user posts 2 tweets per day on average.
*   Each user reads 200 tweets per day on average.
*   Assume a 1:100 write-to-read ratio.

**Traffic/QPS Estimation:**

*   **Write QPS:**
    *   Total tweets per day = 100M users * 2 tweets/user = 200M tweets/day.
    *   Average write QPS = 200M / 100,000 seconds ≈ **2,000 QPS**.
    *   Peak write QPS = 2,000 * 2 = **4,000 QPS**.
*   **Read QPS:**
    *   Total reads per day = 100M users * 200 tweets/user = 20,000M (20B) reads/day.
    *   Average read QPS = 20B / 100,000 seconds ≈ **200,000 QPS**.
    *   Peak read QPS = 200,000 * 2 = **400,000 QPS**.
*   **Conclusion:** The system is heavily read-dominant. This strongly suggests the need for a robust caching strategy.

**Storage Estimation:**

*   **Assumptions:**
    *   Each tweet is ~200 bytes (ID, text, user ID, timestamp).
    *   We want to store tweets for 5 years.
*   **Calculation:**
    *   Daily storage increase = 200M tweets/day * 200 bytes/tweet = 40B bytes/day = 40 GB/day.
    *   Total storage for 5 years = 40 GB/day * 365 days/year * 5 years ≈ 73,000 GB = **73 TB**.
*   **Conclusion:** The storage requirement is significant but manageable. We need a database system that can scale to this size.

By performing these simple calculations, we have already made several key design insights: the need for caching due to high read traffic and the need for a scalable database to handle terabytes of data.
