
# 4.1 Rate Limiting

A rate limiter is a crucial mechanism for controlling the amount of incoming traffic to a service or API. It's a defensive measure that protects your backend services from being overwhelmed, ensures fair resource usage, and mitigates abuse.

## 1. Introduction

**Why is rate limiting important?**

*   **Preventing Abuse:** Protects against malicious actors trying to flood your service with requests (Denial of Service - DoS attacks).
*   **Ensuring Fair Usage:** Prevents a single user or client from monopolizing system resources and degrading the experience for others.
*   **Protecting Backend Services:** Acts as a shield to prevent downstream services (like databases or third-party APIs) from being overloaded.
*   **Cost Control:** For services that rely on paid third-party APIs, rate limiting can prevent unexpected costs.

## 2. Where to Implement Rate Limiting

Rate limiting can be implemented at different places in your technology stack.

*   **Client-Side:** Not reliable. A malicious actor can easily bypass client-side code.
*   **Application Code:** Can be implemented directly within your API server code.
*   **API Gateway / Reverse Proxy (Most Common):** This is often the most effective place to implement rate limiting. It provides a single point of entry to your system, allowing you to enforce rate limits before requests even hit your application servers.

## 3. Rate Limiting Algorithms

### 3.1 Token Bucket

This is one of the most popular and effective algorithms.

*   **How it works:**
    1.  A "bucket" with a fixed capacity (the "burst" size) is configured.
    2.  Tokens are added to the bucket at a constant, fixed rate.
    3.  Each incoming request must consume one token from the bucket to be processed.
    4.  If the bucket is empty, the request is rejected (throttled).
*   **Pros:** Very flexible. It allows for **bursts** of traffic (up to the bucket's capacity) but sustains a steady average rate. It's easy to implement.
*   **Cons:** Can be slightly more complex to tune (requires setting both a bucket size and a token fill rate).

### 3.2 Leaky Bucket

*   **How it works:**
    1.  Incoming requests are placed into a queue (the "bucket").
    2.  The queue is processed at a constant, fixed rate (like a leak from the bottom of the bucket).
    3.  If the queue is full, new requests are rejected.
*   **Pros:** Guarantees a steady, constant outflow of traffic, which can be useful for downstream services that require a stable load.
*   **Cons:** Does not allow for bursts of traffic. A burst of requests will fill the queue and lead to throttling, even if the system has been idle.

### 3.3 Fixed Window Counter

*   **How it works:**
    1.  A time window is defined (e.g., 1 minute).
    2.  A counter is maintained for each user for this window.
    3.  If a request comes in and the counter is below the limit, the request is processed, and the counter is incremented.
    4.  If the counter is at the limit, the request is rejected.
    5.  At the end of the time window, the counter is reset.
*   **Pros:** Very simple to implement.
*   **Cons:** Can allow a "stampede" of traffic at the edge of the window. A user could send their entire quota of requests in the last second of a window and then their full quota again in the first second of the next window, effectively doubling their rate.

### 3.4 Sliding Window (Log & Counter)

These algorithms solve the "edge" problem of the Fixed Window.

*   **Sliding Window Log:** Stores the timestamp of each request in a log. When a new request arrives, it discards all timestamps older than the window and counts the remaining ones to see if the request is within the limit.
    *   **Pros:** Very accurate.
    *   **Cons:** High memory usage, as it stores a timestamp for every single request.
*   **Sliding Window Counter:** A hybrid approach. It maintains a counter for the current window and also considers a weighted value of the counter from the previous window. This provides a good approximation of the sliding window with much lower memory usage.

## 4. Distributed Rate Limiting

In a distributed system with multiple application servers, you need a centralized place to store the rate limit counters. If each server has its own counter, a user could simply round-robin their requests to bypass the limit.

*   **Solution:** Use a centralized, fast data store like **Redis**. Redis is perfect for this because it's an in-memory database and provides atomic operations.
*   **Implementation:** A common approach is to use a Redis script (written in Lua) to perform the "check and increment" logic atomically, which prevents race conditions where multiple requests from the same user are processed concurrently on different servers.

## 5. Rate Limiter Response

When a request is rate-limited, it's important to provide clear feedback to the client.

*   **HTTP Status Code:** `429 Too Many Requests`.
*   **Informative Headers:**
    *   `X-RateLimit-Limit`: The total number of requests allowed in the window.
    *   `X-RateLimit-Remaining`: The number of requests remaining in the current window.
    *   `X-RateLimit-Reset`: The time (in UTC epoch seconds) when the limit will reset.
    *   `Retry-After`: The number of seconds the client should wait before trying again.
