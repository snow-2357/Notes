
# 5.2.4 Case Study: Designing a Component Library

This document provides a practical case study on designing a component library, applying the foundational principles outlined in **[3.3 Component Library Design](./../3.0_Frontend_System_Design_Concepts/3.3_Component_Library_Design.md)**. We will walk through the process of building a single, versatile `Button` component.

## 1. Introduction

The goal of a component library is to create a set of reusable, consistent, and maintainable UI building blocks. This case study will demonstrate the key decisions involved in API design, styling, and tooling for a single, common component.

For a comprehensive overview of the principles, please refer to the main **[Component Library Design](./../3.0_Frontend_System_Design_Concepts/3.3_Component_Library_Design.md)** document.

## 2. Case Study: A Versatile `<Button />` Component

### 2.1 Requirements

Our `Button` component needs to be flexible enough for various use cases.
*   It must have different visual variants (e.g., primary, secondary, danger).
*   It must support different sizes (e.g., small, medium, large).
*   It must have a disabled state.
*   It must be able to contain an icon before or after the text.

### 2.2 Component API (Props)

Based on the requirements, we can define the following props for our React component:

| Prop          | Type                  | Default       | Description                                        |
| :------------ | :-------------------- | :------------ | :------------------------------------------------- |
| `variant`     | `'primary' \| 'secondary' \| 'danger'` | `'secondary'` | The visual style of the button.                    |
| `size`        | `'small' \| 'medium' \| 'large'`      | `'medium'`    | The size of the button.                            |
| `isDisabled`  | `boolean`             | `false`       | If true, the button is disabled and cannot be clicked. |
| `onClick`     | `() => void`          | `undefined`   | Function to call when the button is clicked.       |
| `children`    | `React.ReactNode`     | `undefined`   | The content of the button (usually text).          |
| `leftIcon`    | `React.ReactNode`     | `undefined`   | An icon to display to the left of the content.     |
| `rightIcon`   | `React.ReactNode`     | `undefined`   | An icon to display to the right of the content.    |

### 2.3 Implementation Example (React with CSS-in-JS)

Here is a simplified implementation using React and a CSS-in-JS library like `styled-components`.

```javascript
import styled from 'styled-components';

const StyledButton = styled.button`
  /* Base Styles */
  border: 1px solid transparent;
  border-radius: 8px;
  cursor: pointer;
  display: inline-flex;
  align-items: center;
  gap: 8px;
  font-weight: 600;

  /* Variant Styles */
  ${({ variant }) => variant === 'primary' && `
    background-color: #007bff;
    color: white;
  `}
  ${({ variant }) => variant === 'secondary' && `
    background-color: #f0f0f0;
    color: #333;
    border-color: #ccc;
  `}

  /* Size Styles */
  ${({ size }) => size === 'small' && `
    padding: 4px 8px;
    font-size: 12px;
  `}
  ${({ size }) => size === 'medium' && `
    padding: 8px 16px;
    font-size: 14px;
  `}

  /* Disabled State */
  &:disabled {
    opacity: 0.5;
    cursor: not-allowed;
  }
`;

export const Button = ({
  children,
  variant = 'secondary',
  size = 'medium',
  isDisabled = false,
  leftIcon,
  rightIcon,
  ...props
}) => {
  return (
    <StyledButton
      variant={variant}
      size={size}
      disabled={isDisabled}
      aria-disabled={isDisabled}
      {...props}
    >
      {leftIcon}
      <span>{children}</span>
      {rightIcon}
    </StyledButton>
  );
};

// Usage:
// <Button variant="primary" size="large" onClick={() => alert('Clicked!')}>
//   Click Me
// </Button>
```

### 2.4 Accessibility Considerations

*   The component is rendered as a native `<button>` element, which is crucial for accessibility.
*   The `disabled` attribute handles the visual and functional disabled state.
*   `aria-disabled` is included for better screen reader support.

## 3. Tooling and Infrastructure

Building a single component is one thing; building a library is another. A robust tooling setup is essential.

*   **Development Environment (Storybook):**
    *   **Storybook** is an indispensable tool for developing UI components in isolation.
    *   It allows you to create "stories" for each component, demonstrating its different states and props (e.g., a story for the primary button, another for the disabled state).
    *   This provides an interactive playground for developers and designers and serves as living documentation.
*   **Build Process (Rollup / Vite):**
    *   You need a bundler to compile your library code into a distributable format (e.g., CommonJS, ES Modules).
    *   **Rollup** is a popular choice for libraries because it's optimized for creating small, efficient bundles. **Vite** also has a library mode that uses Rollup under the hood.
*   **Testing:**
    *   **Unit & Integration Tests:** Use a framework like **Jest** with **React Testing Library** to test the component's logic and behavior (e.g., "does the `onClick` handler get called?").
    *   **Visual Regression Testing:** Tools like Chromatic (for Storybook) or Percy take screenshots of your components and compare them on each change to catch unintended visual bugs.
*   **Versioning and Publishing:**
    *   Use **Semantic Versioning** (SemVer) to manage releases.
    *   Publish the packaged library to a registry like **npm** so that it can be installed as a dependency in other projects.

## 4. Conclusion

Designing even a simple `Button` component requires careful thought about its API, styling, and accessibility. Scaling this up to a full library necessitates a strong foundation of tooling for isolated development, testing, and distribution. A systematic approach ensures the final product is robust, maintainable, and easy for other developers to use.
