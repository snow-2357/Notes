# JVM Memory Management in Java

Java manages memory automatically through the **Java Virtual Machine (JVM)**. Understanding how the JVM allocates and deallocates memory is crucial for writing efficient and performant applications.

---

## 1. JVM Memory Structure (Runtime Data Areas)

The JVM divides memory into several distinct areas:

### Heap Memory
The Heap is the largest part of the JVM memory. It's used for dynamic memory allocation for all **Objects** and their instance variables.
- **Shared across all threads.**
- **Managed by the Garbage Collector (GC).**
- Divided into generations: **Young Generation**, **Old Generation** (Tenured), and (previously) PermGen (now Metaspace).

### Stack Memory
Each thread has its own private Stack. It's used for storing **Local Variables**, method call frames, and primitive types.
- **Private to each thread.**
- **LIFO (Last-In-First-Out) structure.**
- Memory is automatically allocated when a method is called and deallocated when the method returns.
- If the stack is full, a `StackOverflowError` is thrown.

### Method Area (Metaspace)
Stores class-level data: class structures, method data, field data, and static variables.
- **Shared across all threads.**
- In Java 8+, PermGen was replaced by **Metaspace**, which uses native memory instead of heap memory.

### Program Counter (PC) Register
Stores the address of the current JVM instruction being executed by the thread.
- **Private to each thread.**

### Native Method Stack
Used for native methods written in C or C++.
- **Private to each thread.**

---

## 2. Heap Memory Generations

Java's Garbage Collector uses a "Generational Hypothesis": most objects die young.

### Young Generation
Where all new objects are initially allocated.
- **Eden Space**: Most new objects start here.
- **Survivor Spaces (S0 and S1)**: Objects that survive a "Minor GC" in Eden are moved here.

### Old Generation (Tenured)
Objects that have survived several rounds of Minor GC in the Young Generation are eventually promoted here.
- **Major GC** (Full GC) cleans up the Old Generation. This is more expensive and time-consuming than Minor GC.

---

## 3. Key Concepts

### Stack vs Heap
| Feature | Stack | Heap |
| :--- | :--- | :--- |
| **Storage** | Local variables, method calls, primitives. | Objects and their instance variables. |
| **Access** | Very fast. | Slower than Stack. |
| **Lifecycle** | Exists only during method execution. | Exists as long as the application runs or until GC. |
| **Scope** | Private to the thread. | Shared by all threads. |
| **Size** | Small, fixed size (configurable). | Large, dynamic size (configurable). |

### Memory Management Errors
- **`OutOfMemoryError` (Heap)**: The JVM cannot allocate more memory for objects because the heap is full and the GC cannot reclaim any more space.
- **`StackOverflowError`**: A method calls itself too many times (e.g., deep recursion), exceeding the stack size.

---

## 4. JVM Memory Tuning

You can configure the JVM memory settings using flags:
- **`-Xms`**: Sets the initial heap size.
- **`-Xmx`**: Sets the maximum heap size.
- **`-Xss`**: Sets the stack size for each thread.
- **`-XX:MetaspaceSize`**: Sets the initial size of Metaspace.

```bash
# Example JVM configuration
java -Xms512m -Xmx2g -Xss1m MyApplication
```

---

## 5. Memory Leaks in Java

Even with automatic GC, memory leaks can occur. A memory leak happens when objects are no longer needed but are still reachable from a root (e.g., a static collection or an unclosed resource).

**Common causes:**
- Static collections that never stop growing.
- Unclosed database connections or file streams.
- Inner classes holding references to their outer classes.
- Poorly implemented `equals()` and `hashCode()` methods in keys used in `HashMap`.
