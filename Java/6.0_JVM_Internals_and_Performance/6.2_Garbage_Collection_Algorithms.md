# Garbage Collection Algorithms in Java

Garbage Collection (GC) is the process by which Java automatically reclaims memory occupied by objects that are no longer reachable from any part of the program.

---

## 1. How GC Works (The Basics)

A GC algorithm typically follows two main steps:
1.  **Mark**: Identifies all reachable objects (starting from GC roots like local variables, static fields, and active threads).
2.  **Sweep/Compact**: Removes unreachable objects and reclaims their memory. Some collectors also compact the heap to eliminate fragmentation.

---

## 2. Common GC Algorithms

### Serial GC (`-XX:+UseSerialGC`)
The simplest GC, which uses a single thread for all GC operations.
- **Good for**: Small applications, single-processor machines, and client-side apps.
- **Downside**: "Stop-The-World" (STW) pauses, where all application threads are blocked during GC.

### Parallel GC (`-XX:+UseParallelGC`)
Also known as the Throughput Collector. It uses multiple threads to perform GC operations in parallel.
- **Good for**: Multi-processor machines and applications that prioritize high throughput (maximum work per unit of time).
- **Downside**: Still causes STW pauses.

### CMS GC (Concurrent Mark Sweep) - Deprecated
Aims to minimize STW pauses by performing most of its work concurrently with the application threads.
- **Good for**: Applications that require low latency.
- **Downside**: High CPU overhead and heap fragmentation.

### G1 GC (Garbage-First) (`-XX:+UseG1GC`)
Introduced in Java 7 and the default GC since Java 9. It divides the heap into regions and prioritizes regions with the most garbage.
- **Good for**: Large heaps (4GB+) and applications requiring low, predictable STW pauses.
- **Key Feature**: Allows setting a target maximum pause time (`-XX:MaxGCPauseMillis`).

### ZGC (Z Garbage Collector) (`-XX:+UseZGC`)
A low-latency, scalable GC introduced as an experimental feature in Java 11 and production-ready in Java 15.
- **Good for**: Very large heaps (up to 16TB) and extreme low-latency requirements (pauses < 1ms).
- **Key Feature**: Performs almost all its work concurrently.

---

## 3. GC Performance Metrics

When tuning your GC, you should consider these metrics:
- **Throughput**: The percentage of total time spent executing application code (vs. spent in GC).
- **Latency (Pause Time)**: The duration of the STW pauses.
- **Footprint**: The amount of memory used by the GC process.

---

## 4. GC Tuning Parameters

- **`-Xms` / `-Xmx`**: Initial and maximum heap size.
- **`-XX:NewRatio=n`**: Ratio of Old to Young Generation.
- **`-XX:SurvivorRatio=n`**: Ratio of Eden to Survivor space.
- **`-XX:MaxGCPauseMillis=n`**: Target maximum pause time for G1 GC.
- **`-XX:+PrintGCDetails`**: Enables detailed GC logging.

---

## 5. Identifying Memory Leaks and Performance Issues

- **VisualVM**: A graphical tool for monitoring and troubleshooting Java applications.
- **JConsole**: A built-in tool that provides information about memory usage, thread count, and GC statistics.
- **Heap Dumps**: A snapshot of the heap memory at a specific point in time. Analyze them using tools like Eclipse MAT (Memory Analyzer Tool).
- **GC Logs**: Analyze logs to identify frequent GCs or long pause times. Use tools like GCEasy to visualize the logs.

---

## 6. Generational Garbage Collection Strategy

As discussed in the previous section, the JVM uses a generational heap.
- **Minor GC**: Occurs in the Young Generation. It's fast and frequent because most objects die young.
- **Major GC (Full GC)**: Occurs in the Old Generation. It's slower and less frequent. A Full GC is usually triggered when the Old Generation is full or when there's an explicit call to `System.gc()` (though this should be avoided).
